지휘 에이전트는 판단하고, 작업 에이전트는 끝까지 수행합니다

일을 받아 판단하고, 맡기고, 확인하는 쪽이 지휘 에이전트(매니저)입니다. 요청서를 받아 끝까지 수행하는 쪽이 작업 에이전트(워커)입니다.

둘 사이의 약속은 요청서와 응답서, 두 파일입니다. 요청서는 목표와 완료 기준을 전달하고, 응답서는 결과와 상태를 돌려줍니다.

에이전트 하나로는 왜 부족할까요?

맥락 창은 한정된 자원이라 일을 나눕니다

에이전트 하나가 계획부터 실행 로그까지 모두 들고 있으면, 맥락 창이 차면서 처음 목표와 완료 조건이 밀려납니다.

그래서 목표를 붙드는 쪽과 실행하는 쪽을 나누고, 둘 사이는 짧은 요청서와 응답서로만 잇습니다.

맡긴 일과 결과는 어떻게 주고받을까요?

두 에이전트는 대화 대신 파일을 주고받습니다

지휘 에이전트가 요청서 파일을 쓰면, 작업 에이전트가 그 파일을 읽고 수행한 뒤 응답서 파일을 씁니다.

파일은 세션이 끊겨도 남고, 다른 에이전트가 나중에 읽어도 같은 내용입니다. 그래서 무엇을 약속했고 무엇이 돌아왔는지 다시 확인할 수 있습니다.

역할을 나누면 무엇이 지켜질까요?

역할을 나누면 세 가지가 지켜집니다

한 에이전트가 계획·실행·확인을 모두 하면 긴 실행 로그가 목표를 밀어내고, 자기 결과를 자기 말로 확인하게 됩니다.

그렇다면 무엇을 직접 하고 무엇을 맡길까요?

지휘 에이전트가 판단하고, 작업 에이전트가 실행합니다

품질을 좌우하는 결정은 위에 남기고, 오래 걸리는 실행만 아래로 내려보냅니다.

직접 할지 맡길지는 일의 무게와 판단의 종류로 정합니다

오래 걸리거나 결과가 큰 일은 맡기고, 읽기·조사·작은 수정은 직접 합니다.

설계·정책·글의 완성도·시각 결과처럼 품질을 좌우하는 판단은 지휘 에이전트가 하고, 실행량만 나눕니다.

맡기기로 했다면 요청서에는 무엇을 적을까요?

요청서는 네 칸이면 충분합니다

요청서는 목표 / 완성 기준 / 참조 경로 / 금지 범위. 판단이 필요한 항목은 매니저가 정해 한 줄씩 적습니다.

사용자가 말하지 않은 범위 축소, 중간 보고 지시, 요청과 무관한 메타 작업은 넣지 않습니다.

등록된 요청은 어떻게 실행될까요?

요청은 한 곳에서 등록하고, 작업 실행기가 이어받습니다

요청은 한 등록 경로를 거쳐 자동 실행기가 작업 에이전트에게 전달하고 실행을 감시합니다. 요청 한 번을 구분하는 요청 ID를 함께 부여합니다.

작업 전 자료 묶음(context pack, 관련 교훈과 결정을 모은 자료)도 전달하며, 구체적인 파일·명령은 위키의 작업 흐름 참조에서 확인할 수 있습니다.

같은 목표를 다시 시도하면 기록은 어떻게 나뉠까요?

목표는 목적, 요청 ID는 한 번의 시도입니다

하나의 목적 아래에서 다시 시도할 때마다 새 요청 ID를 받습니다. 그래서 응답서가 어느 시도의 결과인지 구분할 수 있습니다.

응답서의 처리 상태는 각각 무엇을 뜻할까요?

응답서에는 요청 ID와 처리 상태가 들어갑니다

검증 실패는 이미 만든 산출을 지울 이유가 아닙니다. 승인이 필요하거나 입력·권한이 없고, 같은 오류가 재현되면 멈춰 알립니다.

응답을 받으면 판정하고, 막히면 원인을 고쳐 다시 갑니다

완료 판정에서는 완료 보고 전에 핵심 수치 하나를 원천과 대조합니다. 일부만 끝났으면 한 번 이어가고, 같은 사유로 두 번 막히면 멈추고 알립니다.

시간이 초과되면 같은 크기로 재시도하지 않고, 범위를 나누거나 더 많은 시간을 배정합니다.

지휘 에이전트가 스스로 승인할 수 없는 일은 무엇일까요?

네 가지는 사용자만 승인합니다

사용자만 승인할 수 있는 것은 영구 삭제, 외부 전송·게시, 자격증명·보안 설정, 운영 원칙 수정입니다. 되돌리기 어렵거나 영향이 큰 일이므로 먼저 사용자의 명시적 승인을 받아야 합니다.

그 밖의 결정은 근거와 가정을 기록하고 스스로 진행합니다. 무응답이나 경과 시간은 승인이 아닙니다.
