요청 하나가 확인된 결과가 되기까지

p-hermes는 Hermes가 실제로 일을 나누고, 기록하고, 확인하는 방식을 다섯 강의로 설명합니다.

기준 시점은 2026년 10월 운영 정본입니다. 규칙은 POLICY.md, 작업 에이전트 지침은 WORKER.md, 지식 분류는 CLASSIFICATION.md에서 왔습니다.

대화 하나로 긴 일을 끝까지 이어 갈 수 있을까요?

대화만으로는 긴 작업의 상태가 남지 않습니다

대화는 세션이 바뀌거나 길어지면 목표·진행 상태·다음 행동을 잃습니다. 말로 보고한 결과와 실제 파일이 다를 수도 있습니다.

Hermes는 요청서·JOB 폴더·응답서처럼 파일로 남는 기록을 기준으로 일을 잇습니다.

→ 키를 누르면 아래 줄이 나타납니다.

그 기록을 누가 만들고, 누가 읽을까요?

지휘 에이전트가 목표와 경계를 붙듭니다

지휘 에이전트(매니저)는 요청의 목표와 완료 조건을 정하고, 직접 할 일과 맡길 일을 나눕니다.

읽기·조사·작은 수정과 품질을 좌우하는 판단은 직접 하고, 오래 걸리거나 산출이 큰 실행만 맡깁니다.

맡긴 일은 누가, 어떤 약속으로 처리할까요?

작업 에이전트는 요청서 하나를 한 번에 끝까지 처리합니다

작업 에이전트(워커)는 요청서와 거기 적힌 참조 파일을 읽고, 중간 질문 없이 응답서까지 씁니다.

응답서에는 같은 request_id와 status가 반드시 들어갑니다. 지휘 에이전트는 이를 원 요청과 짝지어 읽습니다.

여러 단계에 걸친 일은 어디에 기록할까요?

기록이 필요한 일은 JOB 폴더와 게이트를 거칩니다

운영 파일을 바꾸거나, 여러 요청에 걸치거나, 나중에 근거로 다시 볼 결정이 있으면 light JOB 하나에 기록합니다.

light JOB은 요청 → 실행 → 검증 → 완료 네 단계이고, 각 전이는 게이트가 필수 파일을 읽은 뒤에만 열립니다.

지난 실패에서 배운 것은 어떻게 다음 작업에 닿을까요?

지식은 작업 앞뒤에 붙습니다

작업 전에는 context pack이 관련 교훈과 결정을 모아 주고, 작업 후에는 다시 쓸 만한 교훈만 knowledge/lessons에 남깁니다.

지식은 후보입니다. 현재 상태는 언제나 실제 파일로 확인합니다.

보고된 결과는 그대로 믿어도 될까요?

검증은 보고 문장이 아니라 실물을 봅니다

지휘 에이전트는 완료 보고 전에 핵심 수치나 주장 하나를 원천과 직접 대조합니다. 시각 산출물은 직접 보고 판정합니다.

확인된 결과·남은 것·교훈을 사용자에게 돌려주면 한 바퀴가 닫힙니다.

두 역할은 정확히 무엇을 주고받을까요?
