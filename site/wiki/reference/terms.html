전체 흐름 속 위치

지휘 에이전트(매니저)가 요청을 정하고 작업 에이전트(워커)가 수행한 뒤, 작업 흐름의 검증 단계에서 결과를 확인합니다. 지휘 에이전트가 보낸 요청은 기본적으로 JOB 없이 바로 처리(simple)되지만, 사용자 직접 승인이 필요한 네 범주는 이 기본값과 상관없이 승인 원문이 있어야 합니다.

이 표는 문서에서 역할 이름과 단계 이름을 일관되게 읽기 위한 대응표입니다.

확정 용어 함께 쓰는 표현·대응 의미와 사용 범위
지휘 에이전트 매니저; 오케스트레이터. POLICY.md가 규칙 정본 목표·완료 조건·경계를 정하고, 직접 할 일과 맡길 일을 나누며, 결과를 원천과 대조해 확인하는 역할. 판단·설계·시각 결과는 직접 하고 실행량만 위임
작업 에이전트 워커; worker_dispatch.py와 WORKER.md가 가리키는 처리 역할 요청서 하나를 읽고 중간 질문 없이 한 번 실행으로 끝까지 수행한 뒤 응답서를 쓰는 역할. 통신은 파일로만
JOB(작업 건) JOB 운영 파일 변경·여러 요청·나중에 근거로 볼 결정이 있는 작업을 기록하는 단위. 사람 대상 설명에서는 “JOB(작업 건)”이라 부릅니다. 구현의 tier 값 light, JOB 없이 처리하는 경로 simple은 코드·명령·필드에서 원래 표기를 씁니다.
작업 흐름 단계 단계 light JOB의 네 단계 request(요청) → execution(실행) → verification(검증) → done(완료)
실행 단계 workflow의 execution 단계 작업 흐름 안에서 승인된 변경을 실제로 적용하는 특정 단계. 일반적인 “작업 수행”의 동의어로 쓰지 않음
작업 수행 수행 역할이 과제를 하는 일반 행위. 단계명인 “실행”과 구분
terminal 상태 done, partial, failed, blocked 응답서가 한 번의 요청 처리 결과로 회신하는 상태. JOB의 단계 상태와 혼동하지 않습니다.
요청 식별자 request_id 한 번의 요청 시도를 가리키는 불변 식별자
목표 식별자 goal_id 여러 요청 시도에 걸쳐 이어질 수 있는 목적의 식별자
사용자 직접 승인 예외 permanent_deletion, external_publication, credential_security, policy_amendment 각각 영구 삭제, 외부 전송·게시, 자격증명·보안 설정 변경, POLICY 개정. 매니저 요청이 기본 simple이어도 사용자 승인 원문이 필요한 범주입니다.

JOB의 request·execution·verification·done은 JOB 흐름의 단계입니다. 응답서의 status는 done·partial·failed·blocked 중 하나로 요청 시도의 결과를 나타냅니다. 코드 식별자, 파일명, 경로, 명령과 API 필드는 원래 표기를 그대로 유지합니다. “지휘 에이전트 / 작업 에이전트”는 역할명이며, orchestrator·worker 같은 코드 이름을 바꾸지 않습니다.
