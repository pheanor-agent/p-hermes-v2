통합 연결 계약 참조

이 페이지는 각 연결점의 형식과 확인 위치를 찾아 쓰기 위한 참조다. 시스템 동작은 문서화된 계약과 공개 예제 범위로 한정하며, 실제 구현의 세부를 추정하지 않는다.

1. 요청서와 응답서

요청서와 응답서는 같은 요청 식별자를 사용한다. 설치된 워커 프로토콜의 필드 예시는 WORKER.md에서 확인한다.

구분문서화된 항목확인점
요청id, profile, requested_at, 목표, 완료조건, 절대경로 참조파일, 제약필수 참조파일 경로와 완료조건 존재 여부
응답원 요청과 같은 ID, 프로필, 완료 시각, terminal 상태, 요약, 절대 산출 경로요청 ID 및 실제 상태 일치 여부

done, partial, failed, blocked는 서로 다른 실제 종결 상태다. 부분 성공은 산출물과 함께 기록하며 검증 실패를 성공으로 숨기지 않는다. 이 페이지에서 다른 프로토콜의 필드명으로 치환하지 않는다.

2. 작업 흐름과 단계 계약

작업 흐름은 단계별 입력·제출물·통과조건을 구분한다. 현재 light-v2 계약의 근거는 작업 흐름 참조와 해당 계약 파일이다. 강의 05는 단계 세부를 복제하지 않고, 작업 흐름 노드의 연결만 보여준다.

  1. 요청과 범위 확인
  2. 단계별 계약에 맞춰 처리
  3. 필요한 승인 경계에서 확인
  4. 실행 결과를 산출물로 보존
  5. 완료조건과 실물을 검증
  6. 사실에 맞는 상태로 응답

단계 이름·요구 파일·검사 명령은 실행 시점의 canonical 계약에서 다시 확인한다.

3. 지식 참조

참조 후보의 목록과 확인된 근거는 구분한다. 워커 지침은 context pack이 있으면 먼저 읽도록 하며, 목록은 참고용이고 판단 근거는 원문에서 확인한다. 원문·출처를 확인하지 못한 자료를 검증된 근거로 연결하지 않는다. 검색 저장소나 색인 구현은 이 항목의 범위가 아니다.

확인 기준: 요청 범위에 맞는 자료인지, 원문을 읽었는지, 근거 상태를 구분했는지 확인한다.

4. 이미지 파이프라인

통합 흐름의 이미지 갈래는 요청 의도 → 카탈로그·구성 → 프롬프트 고도화 → 실행 통로 → 산출물이다. 파이프라인의 공개 계약은 이미지 생성 파이프라인 참조와 이미지 파이프라인 예제에서 확인한다. 이 단계에서 GPU·실제 서비스는 호출하지 않는다.

5. 검증과 결과 전달

완료조건, 응답 상태, 실제 산출물을 대조한다. 생성 성공·품질 확인·게시 상태는 같은 사실이 아니므로 각각 확인한다. 외부 게시를 하지 않는 예제에서도 실제 파일의 존재와 응답 식별자를 확인한다.

검사증거미충족 시
요청 정합요청 ID와 완료조건완료 처리하지 않음
산출 read-back지정 경로의 파일누락 상태를 기록
상태 응답응답서 terminal 값실제 상태로 정정
게시 여부요청된 원격 read-back로컬 성공과 분리 표기

6. 교훈 검토 대기열

검토할 교훈은 후보 상태로 남길 수 있다. 후보 기록만으로 canonical 또는 재사용 지식이 확정되는 것은 아니다. 다음 작업의 근거에 연결하기 전 검토와 결정을 거친다.

7. 통합 예제 실행

예제는 합성 요청·단계 계약·context pack·합성 카탈로그를 연결한다. 가짜 runtime은 이미지 대신 표식 파일을 만든다.

make test
make example NAME=integration-check

정상 fixture는 요청 ID가 같은 done 응답을 내고, 조건 누락·출처 미확인 fixture는 partial로 구분하며 이미 생성한 표식 파일을 보존한다. 네트워크·GPU·외부 서비스 호출은 없다. 상세는 예제 README와 에이전트 과제를 참조한다.
