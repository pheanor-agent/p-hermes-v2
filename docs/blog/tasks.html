작업 상태와 다음 행동 관리하기

에이전트가 여러 단계를 거쳐 일을 수행하면 “무엇을 할 수 있는가”만큼 “지금 무엇을 해야 하는가”가 중요해집니다.

하나의 상태 값만으로는 충분하지 않습니다

작업에는 서로 다른 종류의 진행 정보가 있습니다.

작업에는 서로 다른 종류의 진행 정보가 있습니다. 전체 작업이 어느 단계에 있는지, 현재 어떤 절차를 수행하고 있는지, 내가 보고 있는 정보가 최신인지가 모두 다를 수 있습니다.

이 차이를 구분하지 않으면 상태가 “진행 중”이라는 이유만으로 실제 실행도 정상이라고 생각하거나, 검토 단계라는 이유만으로 필요한 결과물이 이미 준비됐다고 오해하기 쉽습니다. 상태는 현실을 대신하는 값이 아니라 다음 판단에 필요한 정보입니다.

따라서 작업 상태를 볼 때는 단순한 이름보다 지금 무엇이 끝났고 무엇이 남았는지를 함께 확인해야 합니다.

여러 실행이 겹치면 최신 상태를 다시 확인합니다

두 실행이 같은 작업을 동시에 읽은 뒤 서로 다른 변경을 시도할 수 있습니다.

두 실행이 같은 작업을 동시에 읽은 뒤 서로 다른 변경을 시도할 수 있습니다. 한쪽이 먼저 작업을 진행했다면, 다른 쪽이 처음 읽은 정보를 기준으로 계속 움직이는 것은 위험합니다.

p-hermes의 공개 실습은 이런 경우 뒤늦은 변경을 그대로 받아들이지 않고 최신 상태를 다시 확인하도록 만드는 흐름을 보여 줍니다. 중요한 점은 단순히 번호를 맞추는 것이 아닙니다. 앞선 변경 때문에 다음 행동 자체가 달라졌는지 다시 판단하는 것입니다.

이 방식은 여러 에이전트나 도구가 하나의 작업을 함께 다룰 때 특히 중요합니다. 최신 상태를 확인하지 않으면 이미 끝난 단계를 반복하거나 서로의 결과를 덮어쓸 수 있습니다.

계획이 바뀌면 이전 판단도 다시 확인합니다

작업 중에는 요구가 추가되거나 방법이 바뀔 수 있습니다.

작업 중에는 요구가 추가되거나 방법이 바뀔 수 있습니다. 이때 기존 계획에 대한 승인이나 검토 결과를 새 계획에 그대로 적용하면, 실제로 확인하지 않은 내용을 승인한 것처럼 보일 수 있습니다.

그래서 계획 변경은 단순히 새 문장을 덧붙이는 일이 아니라, 무엇이 바뀌었고 어느 단계부터 다시 확인해야 하는지를 구분하는 과정입니다. 반대로 바뀌지 않은 결과까지 모두 버릴 필요는 없습니다. 이미 확인된 부분은 유지하고, 변경의 영향을 받는 부분만 다시 진행하는 편이 효율적입니다.

핵심은 “승인되었다”는 상태보다 무엇에 대해 승인되었는지를 함께 보는 것입니다.

실패와 결과를 모르는 상황은 다르게 다룹니다

명확한 실패는 비교적 다루기 쉽습니다.

명확한 실패는 비교적 다루기 쉽습니다. 문제를 확인하고 조건을 바꾼 뒤 다시 시도하면 됩니다. 더 어려운 경우는 외부 실행을 요청했지만 응답을 받지 못해 실제로 실행됐는지 알 수 없는 상황입니다.

이때 바로 새 실행을 만들면 같은 작업이 중복될 수 있습니다. 먼저 기존 실행의 결과나 기록을 확인하고, 실제 실패인지 단순히 응답만 놓친 것인지 구분해야 합니다. 재시도가 필요하다면 이전 시도와 무엇이 달라졌는지도 남기는 편이 좋습니다.

복구의 목적은 무조건 다시 실행하는 것이 아니라 현재 상태를 다시 확인한 뒤 가장 작은 범위에서 작업을 이어가는 것입니다.

Tasks가 관리하는 것은 상태 이름 자체가 아닙니다. 중간에 변경과 실패가 생겨도 다음 행동을 다시 결정할 수 있는 진행 정보입니다.

구체적인 상태 필드, 변경 규칙, 공개 동시 변경 실습은 [Tasks 기술 명세](/wiki/tasks.html)에서 확인할 수 있습니다.
