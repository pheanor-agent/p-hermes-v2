샷의 목적과 길이를 정하고, 검증한 참조 파일을 편집 계획으로 연결합니다.

샷마다 한 가지 역할을 정합니다

영상의 흐름은 장면의 목적과 길이에서 시작합니다.

LUMA 소개 영상은 제품을 알아보는 장면, 디테일을 보는 장면, 소개 문장을 읽는 장면으로 나눌 수 있습니다. 각 샷이 무엇을 전달하는지 정해야 화면을 바꾸는 이유와 필요한 시간을 설명할 수 있습니다.

샷 계약에는 샷 식별자, 사용할 이미지, 길이와 필요한 조건을 담습니다. 긴 설명을 짧은 샷 안에 억지로 넣으면 읽을 시간이 부족합니다. 편집 전에 샷의 목적과 내용을 함께 확인해야 합니다.

운영 영상 설계는 샷 입력, 참조 방식, 실행 결과와 연결 정보를 다룹니다. 공개 참조 구현은 검증된 이미지 참조와 양의 길이를 받아 연속 시간선을 만드는 부분을 실습합니다.

  • 마무리 샷을 너무 짧게 만들면 어떤 목적이 실패하나요?
영상 · 장면을 시간으로 연결하기 위키공개 구현 소스

역할을 정한 샷을 프로그램이 편집할 수 있는 시간선으로 바꿉니다.

덧붙이는 설명

각 샷에서 무엇을 전달할지 먼저 정한 뒤 장면의 길이와 전환을 선택합니다.

샷의 길이를 더해 시간선을 만듭니다

각 샷의 시작은 앞선 샷의 끝에서 이어집니다.

python
import json
from pathlib import Path
from p_hermes.media import compile_timeline

root = Path("demo-output")
report = json.loads((root / "report.json").read_text())
artifact = report["artifact"]
shots = [
    {"id": name, "duration_seconds": 4,
     "image_ref": artifact["id"], "purpose": name}
    for name in ("intro", "detail", "closing")
]
timeline = compile_timeline(root, shots, [artifact])
print(timeline["duration_seconds"])  # 12.0

샷 길이가 각각 4초라면 LUMA의 12초 시간선은 0–4초, 4–8초, 8–12초입니다. 각 길이는 0보다 커야 하고 합계는 계획한 전달 길이와 일치해야 합니다. 시작과 끝을 따로 입력해 어긋나게 만들기보다 길이에서 계산하면 관계를 명확하게 유지할 수 있습니다.

참조 구현의 compile_timeline은 각 샷의 이미지 바이트를 먼저 확인한 뒤 start_seconds와 end_seconds, 전체 duration_seconds를 계산합니다. 아래 코드는 데모의 한 이미지를 세 샷에서 재사용해 도해와 같은 12초 시간선을 만듭니다. 각기 다른 장면의 실제 이미지는 별도로 준비해야 합니다. CLI 데모가 저장한 두 샷의 5초 시간선은 그대로 유지됩니다.

프레임 기반 편집에서는 시간과 프레임 수의 관계도 확인해야 합니다. 예를 들어 일정한 24fps의 2초 구간은 48프레임입니다. 최종 파일은 인코더와 컨테이너의 시간 표현에 따라 작은 오차가 생길 수 있어 실제 측정값과 허용 오차를 함께 봅니다.

  • 두 번째 샷을 1초 늘리면 세 번째 샷의 시작과 전체 길이는 어떻게 바뀌나요?

계산한 시간선은 편집 입력이 됩니다. 이제 실제 파일이 만들어졌을 때 확인할 내용을 봅니다.

덧붙이는 설명

12초는 블로그·위키 공통 LUMA 기획입니다. 아래 코드는 데모의 한 이미지를 세 샷에서 재사용해 12초 시간선을 계산합니다. 데모 자체가 저장한 두 샷의 5초 시간선은 변경하지 않습니다.

편집 계획과 인코딩 결과를 연결하기

완성 영상의 실제 스트림과 길이를 측정합니다.

shell
p-hermes inspect-video sample.mp4 --duration 2

시간선 JSON은 샷과 참조 파일의 관계를 표현하는 편집 계획입니다. 실제 재생 가능한 영상 파일을 만들려면 별도 인코딩 단계가 필요합니다. 공개 데모는 두 샷의 5초 시간선 JSON을 만들며 영상 인코더나 모델을 실행하지 않습니다.

inspect_video는 ffprobe로 최종 파일의 스트림과 길이, 양수인 화면 크기를 확인합니다. 기대 길이를 전달하면 기본 허용 오차 0.1초 안에 들어오는지도 검사합니다. 특정 목표 해상도와의 일치까지 비교하는 기능은 없으므로 출력된 width와 height를 전달 규격과 직접 대조해야 합니다.

오디오가 필요한 작업이라면 오디오 스트림의 존재와 타이밍도 별도 기준으로 확인해야 합니다. 공개 실습의 영상 규격 검사를 음성 품질이나 시청 경험 전반의 검증으로 확대하지 않습니다.

  • 시간선 파일 생성과 재생 가능한 영상 생성의 차이를 설명해 보세요.

어떤 샷 하나만 실패했다면 전체를 다시 만들 필요가 있는지도 판단해야 합니다.

덧붙이는 설명

영상 규격 실습에는 ffprobe가 필요합니다. 이 검사는 GPU 영상 생성이나 전체 프레임의 시각 검수를 수행하지 않습니다.

실패한 샷부터 영향을 추적합니다

부분 수정 후에는 최종 편집 결과를 다시 확인합니다.

디테일 샷의 제품 색이 다르다면 그 샷의 근거, 이미지, 선택 자원을 따라 원인을 확인합니다. 다른 샷을 무조건 다시 만드는 대신 수정이 영향을 주는 범위를 먼저 정합니다.

샷 파일을 교체하면 digest가 바뀌므로 기존 시간선이 그대로 유효한지 다시 확인해야 합니다. 샷 길이까지 바꿨다면 뒤 샷의 시작점과 전체 길이도 달라집니다. 부분 수정이 끝나도 최종 인코딩 결과의 규격과 시청 흐름은 다시 검수합니다.

복구 가능한 연결은 단순한 편의 기능을 넘어 결과를 설명하는 근거입니다. 어떤 샷을 왜 바꿨고 무엇을 다시 검사했는지 남기면, 완성 파일과 수정 판단을 함께 이해할 수 있습니다.

  • 이미지만 바꾼 경우와 샷 길이도 바꾼 경우의 재검사 범위를 비교해 보세요.
