구도 계획을 실행 입력으로 바꾸고 파일 검사와 시각 검수를 연결합니다.

문구 공간은 구도의 일부입니다

표현 의도를 위치, 규격, 확인 기준으로 구체화합니다.

‘따뜻하고 깔끔한 제품 이미지’라는 표현만으로는 문구를 어디에 놓을지 알 수 없습니다. LUMA 사례에서는 제품을 왼쪽에 놓고 오른쪽에 소개 문장을 위한 공간을 남깁니다. 이렇게 관객의 시선과 편집 목적을 함께 정하면 결과를 평가할 기준이 생깁니다.

이미지 명세에는 제품의 모습, 화면 배치, 출력 규격을 담습니다. 이후 실행 계획으로 번역할 때 필요한 값이 빠져 있다면 이미지 생성 전에 보완합니다. 문구 공간을 선언한 것과 실제로 충분한 공간이 생긴 것은 각각 확인해야 합니다.

공개 데모의 SVG는 제품 왼쪽과 문구 오른쪽 구도를 직접 작성한 실습 파일입니다. CPU로 파일을 만들지만 prompt를 해석해 그리는 생성형 렌더러는 아닙니다. 이미지 컴파일러의 실행 그래프와 SVG 예시 파일을 구분해 살펴봅니다.

제품은 왼쪽에, 문구 공간은 오른쪽에 놓습니다. 구도 조건과 실제 그림을 대조해 보세요.

네 필드가 실행 그래프에 들어갑니다

컴파일은 명세를 검증된 실행 입력으로 바꾸는 단계입니다.

shell
p-hermes compile-image examples/image-request.json image-plan.json

참조 구현의 compile_image는 prompt, width, height, seed를 필수 필드로 받습니다. prompt는 만들 장면의 설명이고 width와 height는 픽셀 규격입니다. seed는 실행 입력을 고정하는 값이며 그 값만으로 모든 환경에서 같은 픽셀을 보장하지는 않습니다.

컴파일러는 카탈로그에서 고른 템플릿과 바인딩을 사용해 각 값을 정확한 입력 위치에 넣습니다. 빠진 필드, 없는 노드, 잘못된 입력 위치는 실행 전에 발견해야 합니다. 입력 템플릿을 보존하므로 같은 템플릿으로 다른 계획을 만들 수 있습니다.

컴파일 결과는 example-graph-v1이라는 공개 예제 계약에 맞춘 그래프입니다. 실제 이미지 엔진에 제출하려면 해당 엔진의 노드 규격과 어댑터가 추가로 필요합니다. 그래프 생성 성공은 입력 바인딩의 성공을 뜻하며 모델 실행과 이미지 생성은 별도 단계입니다.

저장소 루트에서 예제 파일을 컴파일한 뒤 image-plan.json의 workflow.text.inputs.prompt와 workflow.canvas.inputs를 열어 보세요. 명세의 문장과 1280×720 값이 정확한 입력 위치에 들어갔는지 대조할 수 있습니다. 출력 파일은 새 경로를 사용합니다.

결과 파일을 다시 확인할 수 있게 남기기

산출물 기록에는 파일 위치와 내용의 증거가 필요합니다.

shell
p-hermes verify-artifact demo-output/artifact.json --root demo-output

이미지 파일 하나만 전달하면 어느 작업과 계획에서 나온 결과인지 알기 어렵습니다. 산출물에는 파일 위치와 SHA256 digest, 관련 작업과 선택한 자원의 연결을 남깁니다. SHA256은 파일 바이트가 바뀌었는지 비교하는 값입니다.

참조 구현은 허용한 결과 루트 안에 파일이 있는지 확인하고 실제 바이트의 digest와 크기를 검사합니다. 파일이 바뀌거나 루트 밖을 가리키는 참조는 거절합니다. 이미지 형식을 디코딩하는 검사는 없으므로 image라는 미디어 유형 선언과 실제 열리는 이미지는 따로 확인해야 합니다.

이 정보는 다음 영상 단계가 이미지를 사용할 때도 유용합니다. 영상의 샷이 이름이 비슷한 다른 이미지를 참조하는 대신, 검수했던 파일을 정확히 이어받도록 도와줍니다.

규격과 시각 품질을 나누어 검수하기

자동 검사는 구조를, 사람의 관찰은 장면의 목적을 확인합니다.

파일을 읽을 수 있고 지정한 규격이 맞는지 프로그램으로 확인할 수 있습니다. 하지만 램프의 형태가 자연스러운지, 문구와 제품이 경쟁하지 않는지, 전달하려던 분위기가 맞는지는 장면을 직접 살펴야 합니다.

검수 결과는 구체적인 수정 지점을 가리켜야 합니다. 제품이 문구 공간을 침범했다면 구도 명세나 실행 입력을 다시 봅니다. 파일이 손상됐다면 저장이나 전달 단계를 확인합니다. 모든 실패에 같은 프롬프트 수정으로 대응하면 원인을 찾기 어렵습니다.

공개 데모에서는 SVG를 열어 여백과 제품 위치를 확인하고, 파일을 변경해 digest 검사가 실패하는 것도 확인할 수 있습니다. 구조 검사와 시각 검토가 각각 무엇을 증명하는지 나란히 기록합니다.
