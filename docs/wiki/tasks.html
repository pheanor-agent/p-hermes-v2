작업: 다음 행동을 결정하는 상태

목표, 단계, 승인 범위와 실행 근거를 연결하고 충돌이나 중단에서 복구하는 방법을 배웁니다.

이 주제의 강의 보기
목표를 완료 기준으로 바꾸기상태와 단계와 버전은 서로 다른 질문에 답합니다판단을 확인한 뒤 한 번 이동하기동시에 움직인 두 요청을 구별하기중단 원인과 재개 근거를 함께 남기기상태 변경을 검증하는 네 가지 관점공개 실습: 상태와 감사 이력을 같은 트랜잭션에

목표를 완료 기준으로 바꾸기

‘LUMA 소개 자료를 만든다’는 방향은 알 수 있지만 완료 여부는 판단하기 어렵습니다. 이를 ‘확인된 제품 색을 유지한 가로 이미지와 12초 영상, 선택한 구성과 검수 결과를 함께 전달한다’로 바꾸면 산출물과 판정 기준이 생깁니다.

작업 기록은 이 목표를 조사·설계·실행·검토와 연결합니다. 설명을 적은 문서와 실제 상태 기록의 역할을 구별하는 것이 중요합니다. 계획에 ‘검토 완료’라고 써도 실행 결과와 검토 근거가 아직 없다면 완료 상태로 넘어갈 이유는 생기지 않습니다.

상태와 단계와 버전은 서로 다른 질문에 답합니다

운영 구현은 작업의 status, currentStep, workflow.revision을 구분합니다. status는 실행 중인지 중단됐는지 같은 생명주기를, currentStep은 현재 절차 위치를, revision은 변경된 상태의 판본을 나타냅니다. running이라는 값만 읽고 외부 프로세스가 지금 살아 있다고 단정할 수는 없습니다.

workflow-gate는 전이 그래프의 프로필, 그래프 버전과 digest, 허용된 간선을 확인합니다. 상태 저장을 담당하는 mutate-state는 변경 전에 기대한 revision과 선택적인 digest를 비교합니다. 앞쪽은 ‘이 이동이 절차상 가능한가’, 뒤쪽은 ‘내가 본 상태가 아직 최신인가’를 맡습니다.

정보답하는 질문읽는 예
status현재 어떤 생명주기에 있는가?running / failed / interrupted
currentStep어느 절차를 수행하는가?execution_review
workflow.revision어느 상태 판본을 읽었는가?7 → 8
graph version · digest어떤 전이 규칙을 따르는가?등록된 그래프와 일치하는지 비교

판단을 확인한 뒤 한 번 이동하기

정상 흐름에서는 상태를 읽고, 다음 단계에 필요한 산출물과 권한을 확인한 뒤, 허용된 전이를 요청합니다. 변경기는 잠금을 획득하고 최신 상태를 다시 읽습니다. 기대 revision이 맞아야 상태를 변경하고 새 revision을 남깁니다.

현재 운영 변경기는 done으로 이동할 때 execution_review 또는 이미 완료된 위치인지 확인하고 validate_completion을 호출합니다. 이 호출을 읽어 확인했다는 것과 그 하위 검사가 모든 상황에서 충분하다는 평가는 구분해야 합니다. 완료 근거의 내용은 실제 요구와 산출물을 대조해 판단합니다.

동시에 움직인 두 요청을 구별하기

두 실행자가 모두 revision 7을 읽었다고 가정합시다. 첫 요청이 상태를 바꾸면 revision은 8이 됩니다. 두 번째 요청이 ‘7을 읽고 결정했다’고 제출하면 변경기는 이를 거부합니다. 이를 비교 후 교체, CAS라고 부릅니다. 뒤늦은 요청이 최신 판단을 덮어쓰는 일을 줄이는 장치입니다.

거부된 요청은 숫자만 8로 바꾸어 재전송하기보다 현재 단계와 산출물을 다시 읽어야 합니다. 첫 요청이 무엇을 바꿨는지 확인하면 두 번째 행동이 아직 필요한지 판단할 수 있습니다. 원자적 파일 교체는 파일 하나를 온전하게 바꾸는 성질이며, 별도 영수증 파일에 추가하는 쓰기까지 하나의 트랜잭션으로 묶는다는 뜻은 아닙니다.

text
합성 상태 추적
A: revision 7 읽음 → 변경 성공 → revision 8
B: revision 7 읽음 → 변경 요청 → 충돌 거부
B: revision 8 재조회 → 변경 내용 확인 → 다음 행동 재판단

중단 원인과 재개 근거를 함께 남기기

현재 변경기에는 recovery, fail, retry 경로가 있습니다. 실패에는 구체적인 관측 원인을 요구하고, 재시도에는 evidence_delta를 받습니다. ‘실패했다’는 반복보다 ‘참조 파일이 없었고 지금은 권한이 확인된 파일로 교체했다’처럼 달라진 근거가 다음 시도를 설명합니다.

외부 실행에서 응답을 받지 못했다면 실제 작업이 수행됐는지 먼저 재조회합니다. 프로세스나 서비스의 실행 식별자, 결과 파일, 반환 상태가 판단에 도움이 됩니다. 재시도를 결정하기 전에 기존 실행의 결과를 구별하면 중복 작업을 줄일 수 있습니다.

상태 변경을 검증하는 네 가지 관점

정상 전이가 되는지만 검사하면 오래된 revision, 허용되지 않은 단계 이동, 중단 상태에서의 진행, 근거 없는 완료를 놓칠 수 있습니다. 실패 입력도 넣어 상태가 보존되는지 확인해야 합니다. 변경 후에는 새 revision과 현재 단계, 산출물 참조를 다시 읽습니다.

공개 실습의 상태 모델은 이런 비교와 거부를 작은 합성 사례로 보여줍니다. 운영 gate의 모든 플러그인, 백업, 후처리까지 복제하는 모델로 해석하지 마세요. 다음 장에서는 완료한 작업의 정보 중 무엇을 재사용 가능한 지식으로 남길지 살펴봅니다.

공개 실습: 상태와 감사 이력을 같은 트랜잭션에

공개 Store는 SQLite에 작업과 이벤트를 저장합니다. draft에서 approve를 요청하면 approved가 되고, start를 요청하면 running으로 이동하며, 완료·실패·결과 불명을 evidence와 함께 기록합니다. plan을 수정하면 기존 승인을 지우며, 오래된 revision은 거부합니다. 이는 운영 그래프와 독립적으로 작성한 작은 상태 계약입니다.

아래 코드의 approve는 호출자가 제공한 결정을 현재 계획 digest에 연결합니다. 사용자 신원 인증을 수행하는 API는 아닙니다. 상태와 이벤트 쓰기는 같은 SQLite 트랜잭션 안에 있어 함께 반영되거나 함께 취소됩니다.

python
from p_hermes.store import Store

with Store("lesson.sqlite3") as store:
    job = store.create_job("lesson", {"purpose": "구도 계획 검토"})
    job = store.act("lesson", job["revision"], "approve",
                    approved_digest=job["plan_digest"])
    job = store.act("lesson", job["revision"], "start")
    print(job["state"], len(store.events("lesson")))
# running 3  (새 DB에서 1회 실행)
