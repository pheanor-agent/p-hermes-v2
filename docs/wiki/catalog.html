카탈로그: 선택을 실행 가능한 구성으로

모델, 워크플로우, 릴리스와 실행 환경의 관계를 이해하고 선택 조건을 추적합니다.

이름을 고르면 어떤 구성이 따라올까요?

이미지 모델 이름 하나로 실행 조건을 설명하기는 어렵습니다. 같은 계열이라도 워크플로우, 파라미터, 추가 가중치, 실행 환경이 달라지면 입력과 결과가 달라집니다. 카탈로그는 이런 조합에 이름을 붙이고 사용 조건을 함께 관리합니다.

LUMA 사례에서는 ‘가로 구도를 만들고 오른쪽 문구 공간을 확보한다’는 요구가 먼저입니다. 그 요구를 지원하는 후보를 찾고, 검증 상태와 현재 사용 가능성을 확인한 뒤, 선택한 정확한 구성을 실행 입력으로 넘깁니다.

후보 하나를 이루는 구성요소

현재 CatalogInfo에는 family, workflow_id, params와 함께 model, workflow, runtime, release_id, health, verification 등의 정보가 있습니다. CatalogIndex는 카테고리와 카탈로그의 다대다 관계를 읽습니다. 한 후보가 여러 용도에 속할 수 있고 한 용도에 여러 후보가 있을 수 있습니다.

릴리스는 선택한 구성을 특정 판본에 연결하는 데 사용하고, runtime은 실행 환경의 조건을 나타냅니다. health는 시점이 있는 상태 기록입니다. 모델 계열이 같다는 이유로 워크플로우의 노드와 파라미터가 모두 호환된다고 가정할 수는 없습니다.

후보 비교에 이유를 남기기

합성 후보 A는 오른쪽 여백이 있는 가로 이미지용 구성이고, 후보 B는 정사각형 인물 중심 구성이라고 합시다. A를 선택하는 근거는 ‘이름이 익숙해서’보다 명세의 비율과 배치 조건에 맞는다는 설명이 좋습니다. 후보 B를 배제한 이유도 남기면 요구가 바뀔 때 다시 평가할 수 있습니다.

운영 제어 모듈의 scoped_default_diagnostics는 namespace, operation, quality, channel 범위에서 schema_version 3, active, quality 검증, healthy, 기본 선택 가능 조건을 만족하는 후보가 정확히 하나인지 검사합니다. 이 특정 함수의 규칙을 모든 resolver와 모든 스키마의 공통 규칙으로 확대하지 않습니다.

합성 후보명세 적합성판단
A · 가로 제품 구성가로 비율과 오른쪽 문구 영역실행 조건 확인 후 채택
B · 정사각 인물 구성비율과 주요 피사체가 다름이번 요청에서는 제외
A의 오래된 릴리스구성 이름은 같지만 판본이 다름릴리스 참조를 재확인

선택 결과를 실행 입력으로 변환하기

CatalogResolver.to_run_spec은 CatalogInfo 목록을 실행 명세로 바꿉니다. 현재 소스에서 후보의 전체 이름을 variant 식별자로 사용하고, 실행 workflow와 params, enhancer, 선택적인 LoRA 정보를 넣는 변환을 확인했습니다. 별도로 전달되는 프롬프트와 seed도 실행 입력에 참여합니다.

따라서 카탈로그 문서에서 후보 이름만 제시하면 실행을 재현하기 어렵습니다. 어떤 후보의 어느 릴리스를 선택했고, 어떤 프롬프트와 파라미터를 함께 전달했는지를 연결해야 합니다. 해시는 이 참조가 바뀌었는지를 비교할 수 있게 하지만 호환성이나 품질을 대신 판정하지는 않습니다.

같은 요청을 반복했을 때의 판단

카탈로그 제어 모듈은 같은 idempotency key와 같은 plan digest가 이미 있으면 기존 실행 식별자를 재사용하는 결정을 반환합니다. 같은 key에 다른 digest가 오면 충돌을 반환하고, 만료된 계획은 거부합니다. 이는 동일 요청을 구별하는 판단이며 이 함수가 직접 생성 작업을 실행하는 것은 아닙니다.

canonical digest는 변동성 필드를 제거하고 문자열 줄바꿈을 정리한 뒤 정렬된 JSON을 해시합니다. 어떤 필드를 제외하는지에 따라 같은 것으로 취급되는 범위가 달라집니다. 서로 다른 manifest가 모두 SHA-256을 쓴다는 이유만으로 동일한 정규화 규칙이라고 보아서는 안 됩니다.

선택 가능성과 결과 품질을 따로 검사하기

후보가 0개이면 부족한 조건이나 상태를 살피고, 여러 개이면 기본값의 모호함을 해결합니다. health 기록에는 상태를 관측한 시점과 작성 주체가 있어야 합니다. 오래된 healthy 기록만으로 지금의 실행 환경이 정상이라고 결론 내리기는 어렵습니다.

선택이 끝나면 참조 릴리스와 실행 입력이 일치하는지 확인합니다. 생성 뒤에는 출력 파일과 시각 품질을 다시 검사합니다. 다음 장은 선택된 구성에 전달할 시각 의도를 어떻게 명확한 입력으로 바꾸는지 다룹니다.

공개 실습: 판본을 고정하고 바인딩 검사하기

공개 resolve는 asset_id, version, operation, runtime을 명시해 카탈로그 후보를 고릅니다. expected_digest를 전달하면 고정한 내용과 일치하는지도 검사합니다. 현재 운영 resolver를 재배포한 코드가 아니라 선택의 모호함과 변경 감지를 실습하기 위한 독립 계약입니다.

compile_image는 선택 결과의 bindings를 사용해 prompt, width, height, seed를 예제 워크플로우 입력에 연결합니다. 없는 위치나 중복 바인딩을 거부하고 템플릿을 복제해 원본 입력을 보존합니다. 저장소 examples/image-request.json에서 카탈로그·pin·spec·template을 함께 비교할 수 있습니다.

카탈로그 항목의 template_digest는 변환 전 템플릿 전체를 고정합니다. compile_image는 바인딩 위치뿐 아니라 전체 템플릿 해시를 비교하므로, 다른 노드나 숨은 설정이 바뀐 경우에도 실행 입력을 만들기 전에 거부합니다. spec의 값을 바꾸는 실험과 템플릿 자체를 새 판본으로 바꾸는 작업을 구별하세요.

sh
p-hermes compile-image examples/image-request.json image-plan.json
# 새 image-plan.json에 선택 digest와 변환한 워크플로우 기록
