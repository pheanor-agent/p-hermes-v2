영상: 샷을 연결해 시간의 흐름 만들기

샷의 목적과 입력 모드, 계획의 참조, 후보 계보와 편집 검수를 다룹니다.

각 샷에 하나의 역할을 줍니다샷 계약에는 시작과 변화와 끝이 있습니다참조 이미지의 역할에 맞는 입력을 고릅니다실행 계획의 참조를 고정합니다여러 시도에서 선택한 결과를 따라가기샷 검수 뒤에 전체 영상을 봅니다공개 실습: 참조 파일과 타임라인, 실제 영상 검사

각 샷에 하나의 역할을 줍니다

12초 소개 영상을 세 샷으로 나눠 봅시다. 처음 4초에는 제품 전체를 보여주고, 다음 4초에는 빛이 켜지는 변화를 보여주며, 마지막 4초에는 문구를 읽을 시간을 줍니다. 샷마다 역할이 있으면 움직임이 많아도 메시지의 흐름은 단순해집니다.

영상에서는 한 프레임의 품질에 시간적 연결이 더해집니다. 제품 색과 모양이 장면 사이에서 유지되는지, 동작의 시작과 끝이 다음 샷과 이어지는지, 자막과 소리를 이해할 시간이 있는지 확인해야 합니다.

샷 계약에는 시작과 변화와 끝이 있습니다

운영 shot-manifest.v1은 shot_id와 purpose, 양수 duration_seconds, 비어 있지 않은 characters, action의 start/change/end, camera 매핑을 검사합니다. 이 구조는 장면을 ‘무엇을 위해, 누가 또는 무엇이, 어떻게 변하는가’로 설명하게 합니다.

선택적인 audio와 editorial_plan은 음성, 자막, 음악 등의 의도를 담을 수 있습니다. provenance에 출처 패턴 관련 필드가 일부 등장하면 source_pattern_id, source_revision, license_status를 함께 요구합니다. 필드가 있다는 사실만으로 사용 권리가 검증된 것은 아니므로 실제 자료를 공개할 때는 권리 근거를 별도로 확인합니다.

text
합성 샷 S2
목적: 램프의 빛이 켜지는 순간을 전달
길이: 4초
시작: 꺼진 램프를 정면에서 봄
변화: 따뜻한 빛이 점차 밝아짐
끝: 밝기가 안정된 상태를 잠시 유지
카메라: 고정, 제품을 왼쪽에 배치

참조 이미지의 역할에 맞는 입력을 고릅니다

현재 입력 검증기는 t2v, i2v, fl2v, l2v, r2v 모드를 구별합니다. 모드에 따라 첫 프레임, 마지막 프레임 또는 피사체 참조 목록을 요구합니다. 이미지가 하나 있다고 모든 모드에 같은 필드로 전달할 수는 없습니다.

여러 등장 대상을 쓰는 일부 프레임 기반 모드는 프레임에 모두 포함됐는지 또는 대상별 식별 참조가 있는지를 확인합니다. 이는 입력의 대상 범위를 검사하는 규칙입니다. 검증기가 모드를 받아들인다는 사실은 현재 런타임과 모델이 그 모드를 성공적으로 생성했다는 증거와 다릅니다.

모드필수 참조 역할기획 질문
t2v모드별 이미지 필수값 없음텍스트로 어떤 장면을 시작할까?
i2vfirst_frame_asset어떤 화면에서 출발할까?
fl2v첫 프레임 + 마지막 프레임시작과 끝을 어떻게 연결할까?
l2vlast_frame_asset어떤 화면으로 도착할까?
r2vsubject_assets무엇의 정체성을 유지할까?

실행 계획의 참조를 고정합니다

운영 video_run의 계획 검사는 카탈로그, 자산 묶음, 제약, 워크플로우, 런타임 프로필, 프롬프트 컴파일러, resolver 같은 입력 출처와 해시를 다룹니다. 계획이 참조한 구성과 실행 시점의 구성이 바뀌면 결과를 설명하기 어렵기 때문에 연결을 확인합니다.

계획 자체의 해시와 참조 파일의 해시는 서로 다른 역할입니다. 또 자산 검증에는 크기와 수정 시각을 사용하는 캐시 분기가 있어 매번 모든 파일 바이트를 재해시한다고 설명할 수는 없습니다. 계획 검사를 통과한 뒤에도 runtime preflight와 실제 노드 검증, 입력 바인딩이 필요합니다.

여러 시도에서 선택한 결과를 따라가기

candidate_lineage는 attempt, candidate, selected, final 상태를 기록하고, 후보 이후에는 output_hash를 요구합니다. 선택은 정확히 하나여야 하며 final에는 verification=pass가 필요합니다. 어떤 시도에서 나온 결과를 최종으로 채택했는지 읽는 데 도움이 됩니다.

이 입력 검증만으로 전체 사건 순서나 해시와 실제 파일의 일치가 모두 증명되는 것은 아닙니다. 부분 실패가 있다면 성공한 샷을 보존하고 실패한 샷의 입력과 실행 상태를 확인합니다. 기존 실행의 결과가 불명확한 상태에서 새 시도를 만들면 후보가 중복될 수 있으므로 먼저 재조회합니다.

샷 검수 뒤에 전체 영상을 봅니다

샷별 파일의 길이와 해상도, 디코딩, 프레임 레이트를 확인한 뒤 전체 타임라인을 재생합니다. 장면 사이 색과 형태, 움직임 방향, 자막을 읽는 시간, 음성과 화면의 맞물림을 확인합니다. 샷 각각의 PASS를 전체 영상의 PASS로 대신할 수는 없습니다.

세 샷이 각 4초여도 전환 효과나 편집 방식에 따라 최종 길이는 달라질 수 있습니다. 최종 파일을 기준으로 길이와 오디오를 다시 측정하고 직접 재생해 검수합니다. 이 공개 과정의 타임라인은 합성 기획이며 실제 생성 성능이나 편집 파이프라인 실행 결과로 제시하지 않습니다.

공개 실습: 참조 파일과 타임라인, 실제 영상 검사

공개 compile_timeline은 shots와 artifacts를 읽고 참조 이미지 파일의 실제 바이트를 검사한 뒤 각 샷의 시작·끝과 총 길이를 계산합니다. shot 필드는 id, duration_seconds, image_ref, purpose입니다. 이 공개 스키마는 운영 shot-manifest.v1의 모드를 재현하는 스키마와 구별합니다.

실제 영상 파일을 갖고 있다면 inspect-video로 ffprobe 검사를 실행할 수 있습니다. 영상 스트림, 크기, 길이와 파일 해시를 확인하며 기대 길이는 ±0.1초를 허용합니다. ffprobe는 별도 설치가 필요합니다. 샷 사이 정체성과 자막 가독성은 파일 검사 후 직접 재생해 확인하세요.

sh
p-hermes inspect-video your-video.mp4 --duration 5
# 실제 파일이 있어야 실행되며, 검사는 해당 파일의 규격을 확인합니다.
