작업 흐름을 찾아 쓰기

강의 02의 개념을 바탕으로, 현재 분류 기준·단계 계약·검사·실행 경로를 원본 문서에서 확인합니다.

이 페이지의 경로·명령은 사용자 로컬 운영 확장의 좌표입니다. 일반 Hermes 설치나 p-hermes 저장소 복제만으로 제공되지 않습니다. 구성별 범위와 출처 →

1. 처리 경로

작업은 기록 없이 바로 처리하거나 JOB으로 기록할 수 있습니다. 매니저가 보낸 요청은 기본적으로 simple 경로지만, 사용자 승인이 필요한 네 범주를 이 기본값이 면제하지 않습니다. 정본은 아래 경로를 참조하세요.

  • simple: JOB 없이 요청서·대화 범위에서 바로 수행합니다. 매니저 요청(헤더 created_by: orchestrator|heartbeat)은 승인된 실행 지시로 분류되며, 별도 승인 범주에 해당하면 실제 사용자 승인도 있어야 합니다.
  • JOB(작업 건): 운영 파일 변경·여러 요청·나중에 근거로 볼 결정이 있을 때 작업을 기록합니다. 구현의 등급 식별자는 light이며, 실제로 그 일을 하는 에이전트가 네 단계를 거칩니다.

사용자 직접 승인이 필요한 예외는 네 범주입니다. 영구 삭제(permanent_deletion), 외부 전송·게시(external_publication), 자격증명·보안 설정 변경(credential_security), POLICY 개정(policy_amendment). 사용자 승인 원문이 없으면 실행하지 않습니다. 별도 승인이 아닌 조회·일회성 생성·작은 수정은 요청·응답 이력으로 충분할 수 있습니다.

2. 단계 계약

정본은 core/skills/custom/workflow/v2/contract.yaml입니다. JOB 단계는 아래 순서이며 계약은 목적, 입력, 필수·선택 제출물, 통과 조건, 검사, 다음 단계를 정합니다.

  1. request: 범위와 완료 조건 고정; 필수 request.md.
  2. execution: 허용 경계 안에서 수행; 필수 execution.md, 산출물은 요청에 따라.
  3. verification: 테스트와 실물 대조; 필수 verification.md.
  4. done: 근거와 결과 정합 확인; 필수 result.md.

실제 안내 파일: steps/light-request/SKILL.md, steps/execution/SKILL.md, steps/verification/SKILL.md, steps/complete/SKILL.md. 저장소 README와 계약 원문을 함께 읽어 버전 차이를 확인하세요.

3. 실행 및 검사 명령

신규 JOB 생성과 단계 전이는 다음 형태입니다. JOB은 측정 가능한 목표(-g)가 필수입니다.

bash <로컬 운영 루트>/core/scripts/create-job.sh -y --tier light 개선 "작업 제목" -g "측정 가능한 목표와 완료 조건"
python3 <로컬 운영 루트>/core/scripts/context_pack.py <JOB>/request.md --out <JOB>/artifacts/context-pack.md
bash <로컬 운영 루트>/core/skills/custom/workflow/scripts/workflow-gate.sh JOB-XXXX advance

JOB 폴더에는 request.md, approval.md, work-history.md(시간순 결정), artifacts/(분석·초안·로그), execution.md, verification.md, result.md(결과·남은 것·교훈 링크), pre-change/(원본·되돌리기)가 들어갑니다. 각 단계 전이는 gate가 수행하며 누락된 파일·승인 근거는 통과하지 않습니다. 막히면 우회하지 않습니다. 구현은 core/skills/custom/workflow/v2/runner.py, check.sh에서 확인합니다. 이 페이지의 명령은 설명용이며 자동 실행되지 않습니다.

4. 승인 기록

JOB은 실행 단계 전에 JOB 폴더 approval.md에 두 줄이 있어야 게이트가 통과시킵니다.

approved_by: <승인한 사람>
evidence: <사용자 승인 메시지 ID 또는 원문 인용>

매니저 에이전트는 사용자가 대화에서 승인한 문장을 그대로 인용합니다. 작업 에이전트는 승인이 없으면 지어내지 않고 응답서에 승인 요청을 적은 뒤 멈춥니다(WORKER.md 1절). 영구 삭제·외부 전송·게시·자격증명·보안 설정·POLICY 개정은 반드시 사용자 승인 원문이 있어야 합니다(POLICY (i)).

5. timeout과 terminal 결과

요청 응답의 terminal 상태와 JOB의 진행 단계는 서로 다른 상태 체계입니다.

  • 요청 한 번의 응답서: done, partial, failed, blocked로 그 시도의 결과를 알립니다.
  • JOB: request → execution → verification → done 단계로 한 작업의 기록과 검증을 관리합니다. 여기서 done은 JOB 단계이며 응답서의 status 필드와 같은 개념이 아닙니다.

timeout이나 실패 때문에 이미 만든 파일을 버리지 않습니다. 완료 여부는 실행 기록과 파일을 다시 읽어 확인하고, 권장 검증이 미완이면 필수 산출과 구분해 보고합니다.

6. 완주와 복구 규칙

  • 완주 우선(POLICY (0)): 쓸 수 있는 결과를 80~90% 완성도로 끝까지 만들고, 남은 부분은 실사용 피드백으로 다듬습니다.
  • partial은 원 목표 + 직전 실패 원인 1줄 + 바꾼 점 1줄 + 남은 항목으로 이어가기 1건, timeout은 한 단계 올리거나 나눕니다(POLICY (a-4)).
  • 같은 goal에서 blocked 2회 또는 partial 3회 연속이면 원인을 한 번 진단하고 진단 기록 전까지 반복하지 않습니다.
