진행 상태와 현재 단계를 함께 읽기두 작업자가 같은 상태를 바꿀 때승인을 구체적인 계획에 연결하기결과가 불명확하면 먼저 조회합니다
02 / 01 · 작업 · 진행을 이어가는 구조

진행 상태와 현재 단계를 함께 읽기

상태는 일의 상황을, 단계는 지금 확인할 내용을 말합니다.

작업이 진행 중이라는 말만으로는 다음 행동을 결정하기 어렵습니다. 목표와 완료 기준, 현재 단계, 수정 번호가 함께 있어야 지금 계획을 검토 중인지 결과를 검사 중인지 알 수 있습니다. 운영 작업 구조의 status, currentStep, revision은 서로 다른 정보를 담습니다.

공개 참조 구현은 별도 계약의 작업 레코드와 사건 기록을 사용합니다. 운영 시스템의 모든 상태를 그대로 복제하는 대신, 계획을 승인하고 실행을 시작하고 결과를 확인하는 핵심 경계를 재현합니다. 두 구현의 이름이 비슷해도 완전한 호환성을 뜻하지 않습니다.

램프 사례의 완료 기준은 계획을 작성하는 것만으로 끝나지 않습니다. 이미지와 영상의 산출물, 확인 결과, 연결된 근거를 살핀 뒤 완료를 판단합니다. 다음 행동은 상태 문자열과 그 상태를 뒷받침하는 기록을 함께 읽고 결정합니다.

  • 단계가 같아도 상태가 달라질 수 있는 예를 들어 보세요.

발표자 설명

status와 currentStep을 혼용하지 않게 설명하고 공개 구현의 계약을 구별합니다.

02 / 02 · 작업 · 진행을 이어가는 구조

두 작업자가 같은 상태를 바꿀 때

이전 수정 번호를 제시해야 안전하게 다음 상태를 쓸 수 있습니다.

python
from p_hermes.store import Store

with Store("exercise.sqlite3") as store:
    job = store.create_job("lamp-task", {"purpose": "Prepare a lamp image"})
    job = store.act(job["id"], job["revision"], "approve",
                    approved_digest=job["plan_digest"])
    job = store.act(job["id"], job["revision"], "start")
    # state: running, revision: 2

두 작업자가 수정 번호 3의 기록을 읽었다고 해 봅시다. 첫 작업자가 상태를 갱신해 수정 번호를 4로 만들면, 두 번째 작업자의 판단은 이미 오래된 상태를 전제로 합니다. 이를 그대로 저장하면 먼저 기록한 결과를 덮어쓸 수 있습니다.

비교 후 변경, 즉 CAS는 쓰기를 요청할 때 예상 수정 번호를 함께 전달하는 방식입니다. 저장된 번호와 다르면 변경을 거절합니다. 두 번째 작업자는 최신 레코드와 사건 기록을 다시 읽은 뒤 자신이 하려던 변경이 여전히 맞는지 판단해야 합니다.

참조 구현은 SQLite 트랜잭션 안에서 상태 변경과 사건 기록을 함께 저장합니다. 하나가 실패하면 둘 다 반영되지 않아, 상태만 바뀌고 설명 기록은 없는 불일치를 줄입니다. 이 보장은 같은 저장소 안의 변경에 적용됩니다.

02 / 03 · 작업 · 진행을 이어가는 구조

승인을 구체적인 계획에 연결하기

계획이 달라지면 이전 승인이 무엇을 허용했는지 다시 확인합니다.

‘제작해도 된다’는 승인을 계획과 별개로 저장하면, 이후 영상 길이나 사용 자원이 바뀌어도 같은 승인으로 실행될 수 있습니다. 승인 당시의 계획 내용에 고유한 요약값인 digest를 연결하면 이런 변화가 드러납니다.

참조 구현은 계획의 digest를 승인에 묶습니다. 실행 직전 계획이 달라졌다면 승인된 값과 현재 값이 일치하지 않아 진행을 막습니다. digest는 내용을 읽기 쉽게 설명하는 문서를 대신하지 않으므로, 사람이 볼 수 있는 계획도 함께 남겨야 합니다. 이 승인 동작은 로컬 호출자가 판단을 기록하는 기능이며, 호출자의 신원을 확인하는 인증 서비스는 아닙니다.

램프의 세 샷을 다섯 샷으로 늘리는 것은 단순 오탈자 수정과 다릅니다. 바뀐 계획을 검토하고 새 허용 범위를 확인해야 합니다. 이때 작업 기록은 변경 전후의 내용을 찾아갈 연결점이 됩니다.

발표자 설명

해시가 승인의 의미를 자동으로 결정하는 것은 아니며 내용 변경을 감지하는 장치임을 강조합니다.

02 / 04 · 작업 · 진행을 이어가는 구조

결과가 불명확하면 먼저 조회합니다

재개는 마지막으로 확인된 사실에서 시작합니다.

외부 실행 요청 뒤 연결이 끊기면 실행이 시작되지 않았는지, 실행은 끝났지만 응답만 유실됐는지 바로 알 수 없습니다. 실패라는 한 단어로 합치면 같은 생성을 다시 요청해 중복 비용이나 파일을 만들 수 있습니다.

작업에는 마지막 요청과 관측 결과를 남깁니다. 결과가 불명확한 경우 먼저 제공자의 실행 식별자나 저장된 결과를 조회하고, 확인된 사실을 바탕으로 복구합니다. 참조 구현의 복구 경계 역시 외부 결과를 아는 척하는 자동 성공 처리를 허용하지 않습니다.

완료 판단은 결과 파일의 존재, 파일 내용 검증, 요구 충족 확인을 모아 내려야 합니다. 참조 구현의 complete는 비어 있지 않은 evidence를 받으며, 그 설명의 사실 여부를 자동으로 검증하지 않습니다. 데모는 호출 전에 파일과 시간선을 확인합니다. 운영에 연결할 때는 이런 검수를 완료 전제조건으로 묶어야 합니다.

  • 결과 불명과 확인된 실패에서 다음 행동은 어떻게 달라지나요?
