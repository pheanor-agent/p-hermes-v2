## 자체 요약

모델과 환경 사이의 하네스를 prompt/persona, tool surface, rollout protocol, context manager, memory, sub-agent topology, guardrail, verifier, observability 등으로 나눈다. 하네스를 OS에 비유하되, 모델 역량이 상승하면 한때 필요한 scaffolding이 불필요한 유지보수 부채가 될 수 있으므로 하네스의 구성요소를 영구 제품 표면으로 가정하지 말라는 논지다.

## 상세 정리
### 핵심 주장
- 하네스는 모델과 모델이 작동하는 환경 사이의 오케스트레이션 층이다. 저자는 이를 운영체제에 비유한다. 모델은 CPU에 해당하고, 하네스가 인터럽트, 외부 인터페이스, 프로세스 관리, 문맥 관리를 맡는다.
- 논지의 핵심은 기술 부채다. 많은 팀이 하네스 코드를 영구적인 제품 표면으로 취급하지만, 모델 능력이 올라가면 하네스 로직의 상당 부분이 모델 안으로 흡수되어 사라질 수 있다는 것이다.
- 따라서 하네스를 과하게 쌓는 것은 잠재 부채이며, 구성요소마다 "지금도 필요한가"를 따로 물어야 한다고 주장한다.

### 구조와 패턴
- 저자는 하네스를 아홉 층으로 나눈다: 시스템 프롬프트와 페르소나, 도구 표면, 롤아웃 방식(단일 턴, 다중 턴, ReAct, 계획 후 실행 등), 문맥 관리자, 메모리, 하위 에이전트 구조, 가드레일과 게이트, 검증자와 판정자, 관측성.
- 하네스는 두 종류로 나뉜다. 모델 제작자가 배포하는 내부 하네스와, 사용자가 그 위에 얹는 외부 하네스다. 두 층은 변화 속도와 누적되는 부채의 종류가 다르다.
- 운영 하네스는 최소 권한과 기본 거부를 따르는 제약 표면이고, 학습·연구 하네스는 탐색을 위해 넓게 열린 표면이라는 대비를 제시한다.

### 적용 방법
- 하네스 구성요소를 목록으로 만든 뒤 각 항목에 제거 조건을 붙인다. 모델이 바뀌면 다시 평가할 항목으로 표시해 두면 부채가 쌓이는 속도를 볼 수 있다.
- 실행 환경 쪽 제약(도구 허용 목록, 자격 증명 범위, 승인 단계)은 프롬프트 지시보다 도구 구성으로 강제하는 것이 원문의 권고다.
- 실측 대조는 별도로 한다. 원문은 논설적 관찰이므로, 해당 하네스의 실패율과 비용 데이터를 보고 구성요소를 줄일지 결정한다.

### 근거와 한계
- 원문 일부 확인: 본문 앞부분과 뒷부분, 참고문헌 목록은 확인했고 중간 절은 열람하지 않았다. 그래서 원문이 제시하는 세부 실험 설계와 수치는 이 정리에 포함하지 않았다.
- 원문이 인용하는 제3자 실험(내부 하네스와 외부 하네스의 벤치마크 격차)은 원문 주장이며, 조건이 바뀌면 결과도 달라질 수 있다.
- 저자가 말하는 "흡수"는 전망이다. 특정 구현이 실제로 부채가 되었다는 실측은 원천에 없다.

## Hermes 관련성

용어 범위를 넓히고 외부 하네스 사례를 비교할 때 유용하다. 논설적 전망이며 Hermes 구현이 실제로 부채가 되었거나 폐기되어야 한다는 실측은 아니다. 현재 실패·비용·운영 데이터를 별도로 대조해야 한다.
