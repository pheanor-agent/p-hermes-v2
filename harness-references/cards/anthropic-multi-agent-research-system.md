## 자체 요약

리드 에이전트가 질의를 계획하고 서로 독립적인 탐색을 병렬 subagent에 위임하는 연구 시스템을 설명한다. breadth-first 탐색에서 병렬화가 강점을 보일 수 있지만, 시스템 구성·작업 분해·결과 합성·비용과 latency trade-off가 핵심이다. 공개된 성과 수치는 Anthropic 내부 평가의 출처 주장으로 취급한다.

## 상세 정리

### 핵심 주장
- 연구처럼 경로를 미리 정할 수 없는 열린 문제에는 다중 에이전트 구조가 맞는다고 본다. 리드 에이전트가 질의를 계획하고, 독립적인 탐색을 병렬 subagent에 맡긴 뒤 결과를 합성한다.
- 필자들의 내부 평가에서 Opus 4를 리드, Sonnet 4를 subagent로 쓴 구성이 단일 Opus 4 에이전트보다 90.2% 높았다는 수치를 제시한다. 이는 실험 조건(내부 연구 평가셋)을 전제로 한 출처 주장이며, 독립 재현 결과는 아니다.
- 성능 분산의 설명 요인을 분석한 결과, BrowseComp 평가에서 토큰 사용량이 약 80%의 분산을 설명했고 도구 호출 수와 모델 선택이 나머지를 설명했다고 보고한다.
- 대가는 크다. 에이전트는 채팅보다 약 4배, 다중 에이전트는 약 15배 토큰을 쓴다. 따라서 과제 가치가 높고 병렬화가 가능한 경우에만 경제성이 있다고 결론짓는다.
- 모든 agent가 같은 컨텍스트를 공유해야 하거나 의존성이 많은 과제(예: 많은 코딩 과제)에는 맞지 않는다고 명시한다.

### 구조와 패턴
- 오케스트레이터-워커 패턴이다. 리드 에이전트는 계획을 메모리에 저장해 컨텍스트 한계에서도 계획이 보존되게 하고, subagent는 각자 검색과 평가를 반복한 뒤 발견 사항을 돌려준다.
- 인용은 별도의 인용 에이전트가 최종 문서에서 출처 위치를 찾아 붙이는 단계로 분리한다.
- 결과 전달은 결과물을 파일시스템에 저장하고 가벼운 참조만 조정자에게 넘기는 방식을 권한다. 대화 이력으로 큰 산출물을 옮기면 정보 손실과 토큰 낭비가 생긴다는 근거다.

### 적용 방법
- 독립적인 조사 축이 여럿 있는 과제에서만 fan-out을 쓰고, 순차 의존 과제는 단일 에이전트로 두는 기준을 먼저 세운다.
- subagent 수와 도구 호출 상한을 프롬프트에 명시하지 않으면 과도한 생성이 생긴다는 실패 사례가 보고되어 있으므로, 생성 상한을 설계에 포함한다.
- 긴 작업은 단계 요약을 외부 메모리에 저장하고, 필요 시 깨끗한 컨텍스트의 새 subagent로 이어가는 방식을 검토한다.
- 평가는 중간 과정이 아니라 최종 상태 기준으로 체크포인트를 나누는 방식이 상태 변경 작업에 더 적합하다고 제안한다.

### 근거와 한계
- 원문 일부 확인: 원문 앞부분(구조, 성능 분석)과 뒷부분(프롬프트 원칙, 평가 원칙)을 읽었다. 중간의 세부 프롬프트 원칙은 추출에서 생략되어 확인하지 못했다.
- 90.2% 등 수치는 Anthropic 내부 평가 결과이며, 과제 구성과 평가 방식이 공개 벤치마크와 같지 않다.
- 토큰 사용 설명 비율(80%, 95%)도 해당 평가 세트의 분석 결과다. 다른 과제에서 같은 비율이 나온다는 근거는 아니다.
- 글 작성 시점은 2025년 6월 검색 결과 기준으로 확인했으며, 본문 재확인은 하지 않았다.

## Hermes 관련성

독립 조사 태스크가 다수인 경우 fan-out의 이점을 검토할 때 참고할 수 있다. 일반 코딩이나 서로 의존하는 일에 병렬화가 우월하다는 보편적 증거가 아닙니다.
