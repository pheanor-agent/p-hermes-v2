## 자체 요약

에이전트 시스템 구축에서 모델 능력 외의 어려움—환경, 도구, 피드백, 반복 실행 및 실패 처리—을 다루는 실무 관점 글이다. 상세한 주장은 원문을 기준으로 확인해야 하며, 여기서는 특정 해결책·수치에 관한 보증을 옮기지 않는다.

## 상세 정리

### 핵심 주장
- 에이전트 구축의 어려움은 모델 능력보다 도구 사용의 실제 마찰(환경, 도구 결과, 실패 처리, 반복 실행)에서 나온다는 것이 글의 중심이다.
- 필자는 범용 SDK나 고수준 추상화(예: 여러 provider를 묶은 AI SDK)를 쓰기보다 provider SDK를 직접 쓰고 agent loop를 직접 구동하는 편을 택했다. 실제 도구 사용에서 추상화가 깨지고, 공급자 간 차이를 흡수할 올바른 agent 추상화가 아직 정립되지 않았다는 판단이다.
- 캐싱은 플랫폼에 맡기기보다 직접 관리하는 편이 비용과 캐시 적중을 예측하기 쉽다고 본다. 다만 컨텍스트 편집은 캐시를 무효화하므로 비용 trade-off가 명확하지 않다고 적는다.
- 루프 안의 '강화(reinforcement)'가 생각보다 큰 역할을 한다. 도구 결과에 목표와 작업 상태를 다시 넣고, 백그라운드 상태 변화를 알리며, 실패 후 되돌아가야 할 단계를 알려주는 방식이다.
- 실패는 컨텍스트에서 격리해야 한다. 반복이 필요한 작업은 subagent에서 성공할 때까지 돌리고 성공과 실패 접근의 요약만 상위로 올리는 방식을 제안한다.
- 파일시스템 같은 공유 상태 계층이 중요하다. 한 도구의 산출물을 다른 도구(예: 코드 실행)가 읽을 수 있어야 '막다른 길(dead end)'이 없는 구조가 된다.

### 구조와 패턴
- 기본 루프는 단순하지만, 도구 구성에 따라 캐시 제어, 강화 방식, 도구 프롬프트, provider 측 도구 요구가 달라진다.
- 상태 공유는 가상 파일시스템으로 구현하며, subagent와 subinference가 같은 저장 위치를 본다.
- 실패 처리는 두 경로다. 별도 subagent로 격리하거나, 컨텍스트 편집으로 실패 출력을 걷어내되 '무엇이 안 됐는지'만 남긴다.

### 적용 방법
- 다중 provider 추상화를 먼저 만들기보다 실제 도구 사용 사례에서 필요한 추상화만 점진적으로 쌓는 접근이 필요하다는 점을 설계 체크리스트로 삼을 수 있다.
- 도구 호출 결과에 목표·작업 상태를 재주입하는 로직과, 재시도 시 이전 단계로 돌아가야 하는지 알리는 메시지를 분리해 설계하는 방식을 검토할 만하다.
- 실패가 잦은 작업은 독립 실행 단위로 격리하고, 상위에는 성공 결과와 짧은 실패 요약만 전달하도록 경계를 긋는다.

### 근거와 한계
- 원문 일부 확인: 원문 페이지를 열어 앞부분과 뒷부분을 읽었다. 중간 구간(일부 도구 출력 설계와 모델 선택 논의)은 추출 과정에서 생략되어 직접 확인하지 못했다.
- 2025-11-21 작성된 개인 실무 기록이며, 필자 본인이 밝힌 대로 '현재 상황' 관찰이다. 모델별 캐시 동작이나 특정 제품 동작은 시점에 따라 달라질 수 있다.
- 정량 벤치마크나 통제된 비교 실험은 없다. 모든 주장은 필자의 경험에 따른 관찰로 읽어야 한다.
