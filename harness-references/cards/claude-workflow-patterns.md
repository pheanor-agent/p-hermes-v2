## 자체 요약

고정 순서의 sequential, 독립 작업의 parallel, 평가 후 반복 개선하는 evaluator-optimizer 패턴을 비교한다. 먼저 단일 agent로 시도하고, 실제 latency 병목·독립성·측정된 품질 향상이 확인될 때에만 더 복잡한 패턴을 선택하라고 권한다.

## 상세 정리

### 핵심 주장
- 여러 에이전트를 함께 쓸 때 핵심 결정은 어떤 워크플로 패턴을 고르느냐이며, 실무에서는 순차(sequential), 병렬(parallel), 평가-최적화(evaluator-optimizer) 세 패턴이 대부분의 경우를 덮는다고 주장한다.
- 패턴은 고정된 템플릿이 아니라 조합하고 중첩할 수 있는 빌딩 블록이라고 본다.
- 기본 권고는 가장 단순한 패턴부터 시작하는 것이다. 단일 에이전트로 충분하면 워크플로를 쪼개지 않고, 지연이 실제 병목이며 작업이 독립적일 때만 병렬을, 품질 향상을 측정할 수 있을 때만 평가 루프를 추가하라고 한다.
- 워크플로는 에이전트의 자율성을 없애는 장치가 아니라, 전체 흐름의 순서와 체크포인트, 각 단계의 경계를 정해 자율성이 작동할 범위를 제한하는 장치라고 설명한다.

### 구조와 패턴
- 순차 패턴은 단계 사이에 의존성이 있을 때 쓴다. 앞 단계의 출력을 다음 단계가 받아 처리하며, 지연이 늘어나는 대신 단계별 집중으로 정확도를 얻는다고 기술한다. 초안-검토-다듬기 사이클이나 추출-검증-적재 파이프라인이 예로 든다.
- 병렬 패턴은 독립된 하위 작업을 동시에 실행한 뒤 결과를 합친다. 분산 시스템의 팬아웃·팬인에 비유된다. 여러 품질 차원 평가, 취약점 범주별 코드 리뷰, 문서의 주제·감성·사실 검증 분담이 예다. 비용은 동시 호출만큼 늘고 결과를 집계하는 전략이 필요하다.
- 평가-최적화 패턴은 생성 에이전트와 평가 에이전트가 기준을 충족할 때까지 반복한다. 생성과 평가를 서로 다른 인지 작업으로 보고 분리하는 것이 핵심이다. 측정 가능한 기준이 있어야 하며, 최대 반복 횟수와 품질 임계값을 시작 전에 정하라고 권한다.
- 세 패턴은 문제 유형, 지연, 토큰 비용, 신뢰성 측면의 장단점 표로 비교된다.

### 적용 방법
1. 단일 에이전트가 프롬프트 안의 단계로 처리할 수 있는지부터 시험한다.
2. 실패가 특정 단계에서만 나면 그 단계를 순차 파이프라인으로 분리한다.
3. 독립된 하위 작업이 있고 지연이 실제 병목일 때 병렬화한다. 결과를 합치는 규칙(다수결, 신뢰도 평균, 가장 전문적인 에이전트 우선 등)을 구현 전에 정한다.
4. 품질 기준을 평가자가 일관되게 적용할 수 있을 때 평가-최적화 루프를 넣는다. 린터처럼 결정적 도구가 있다면 그것을 먼저 쓴다.
5. 반복 상한과 품질 임계값을 먼저 설정한다. 평가자가 사소한 지적만 반복하는 정체 구간에서 멈추는 기준도 함께 둔다.
글은 패턴을 모듈형으로 보고, 순차 흐름에 병렬 단계를 덧붙이거나 나중에 평가를 추가하는 식의 점진적 진화를 권한다.

### 근거와 한계
- 세 패턴의 장단점은 저자 팀들의 실무 경험에 기반한 정성적 설명이다. 패턴별 통제 실험이나 정량 비교 수치는 본문에 제시되지 않았다.
- 병렬화로 얼마나 빨라지는지, 평가 루프가 얼마나 품질을 올리는지에 대한 본문의 일반론은 조건 없이 옮기면 안 된다.
- 페이지에는 2026년 3월 5일 게시로 표시되어 있으나, 카드 메타데이터의 게시일은 "미확인"으로 남아 있다. 본 정리는 페이지 표시를 기준으로 하되 확정은 아니다.
- 원문 페이지의 앞부분, 중간 대부분, 끝부분을 확인했으나 추출 과정에서 일부 구간이 생략되었다. 본문에 언급된 백서는 열람하지 않았다.
- 권리 상태는 미확인이므로 요약과 구조 설명만 적었다.

## Hermes 관련성

작업 그래프·위임·review topology를 고를 때 간단한 선택 기준이 된다. 저자의 패턴 설명이지 각 구조의 통제된 비교 결과나 Hermes 도입 근거는 아닙니다.
