# p-hermes 강의 상세 설계 — 키워드와 동작을 연결하는 6편 구성

2026-09-10 · 개정 3 · 상태: HTML 강의 구현 기준

현재 기준 문서다. 이번 설계는 전체 강의 1편과 분야별 강의 5편으로 교체하고, 키워드 정의·학습 순서·관심 환기·매체·검증을 구체화한다. 여섯 HTML 강의와 이미지·영상 자산을 구현하고 실제 화면을 검토했다. 배포 대상은 GitHub Pages이며, 사용자 요청에 따라 PDF 배포는 범위에서 제외했다. 기존 블로그 전환은 완료된 상태다.

## 1. 설계의 기준

청중은 각 분야의 핵심 용어를 알아보고, 자기 말로 뜻을 설명하며, 새로운 입력이나 실패 사례에 그 개념을 적용할 수 있어야 한다. 용어의 개수나 슬라이드의 미감만으로 달성 여부를 판단하지 않는다.

기술에 관심이 있고 개발 경험이 섞여 있는 청중을 가정한다. 전체 강의는 60분, 분야별 강의는 각각 75분이다. 각 강의의 마지막 10분은 질의응답이며, 본편에 짧은 예측·회상·실습 시간을 포함한다. 총 435분, 7시간 15분의 콘텐츠다. 한 자리에서 연속 진행할 경우 휴식은 별도로 추가하며, 기본 제공 형태는 각각 독립적으로 듣는 6편이다. 실제 청중과 리허설 결과에 따라 시간을 조정한다.

| 강의 | 목표 | 본편 / 질문 | 핵심 키워드 |
|---|---|---|---|
| 00 전체 구조 | 다섯 분야의 역할과 주고받는 자료를 설명한다 | 50 / 10분 | 역할, 상태, 근거, 계약, 산출물, 추적 |
| 01 작업 | 상태 변경의 조건과 안전한 복구 판단을 설명한다 | 65 / 10분 | 상태, 단계, 리비전, 승인, 트랜잭션, 복구 |
| 02 지식 | 자료가 재사용할 지식이 되는 과정과 검색 결과의 유효성을 판단한다 | 65 / 10분 | 출처, 정규화, 등록, 인덱스, 검색, 갱신, 퇴역 |
| 03 카탈로그 | 사용할 자원을 고르고 실행할 구성의 동일성을 확인한다 | 65 / 10분 | 자산, 메타데이터, 호환성, 선택, 버전 고정, 해시, 바인딩 |
| 04 이미지 | 의도를 실행 입력으로 옮기고 결과의 규격과 구도를 검수한다 | 65 / 10분 | 명세, 구도, 프롬프트, 컴파일, 파라미터, 검수 |
| 05 영상 | 샷·참조·시간의 관계와 수정 후 확인할 범위를 설명한다 | 65 / 10분 | 샷, 참조, 타임라인, 연속성, 편집, 검수 |

전체 강의는 큰 구조를 이해하는 출발점이다. 분야별 강의는 개념·구조·실제 입출력·실패·수정의 깊이를 본편에서 다룬다. 중요한 구현 설명을 부록으로만 넘기지 않는다. 각 강의 첫 장면에 필요한 선행 용어를 짧게 다시 설명하므로, 개별 강의부터 들어도 따라갈 수 있다. 영상 강의는 이미지 강의의 산출물·검수 개념을 짧게 복습한다.

다섯 분야, 개념부터 기술까지의 깊이, HTML 발표와 GitHub Pages 접근, 세심한 흐름, 다양한 직관적 표현, 실제 가독성 검증을 유지한다. LUMA를 전편의 중심으로 두지 않는다. 작업·지식·카탈로그에는 기능에 직접 맞는 사례를 쓰고, 이미지·영상에 LUMA를 연결 사례로 쓴다.

## 2. 키워드를 인지하고 기억하게 하는 방식

### 2.1 용어의 층위

- **핵심 키워드:** 각 강의에서 6–7개. 이 수는 이번 편집의 출발점이며 보편적인 기억 한계 수치가 아니다. 장 제목, 정의, 도해 라벨, 회상 질문에서 같은 표기를 쓴다.
- **보조 용어:** 핵심 동작을 설명할 때 필요한 CAS, digest, 입력 슬롯, 프레임레이트 등. 처음 등장할 때 바로 풀어 쓰고 해당 핵심 키워드에 연결한다. 별도 암기 목록으로 늘리지 않는다.
- **코드 식별자:** `approved_digest`, `image_ref` 등. 핵심 용어 옆에서 실제 구현과 대응시킨다. 코드 식별자를 설명 없이 새 개념처럼 제시하지 않는다.

예를 들어 화면의 중심 용어는 **리비전**이다. 먼저 “변경 전후를 구분하는 상태의 번호”라고 정의하고, 두 수정의 번호를 비교하는 장면에서 **비교 후 갱신(CAS)**을 보조 용어로 소개한다. 실제 코드에서는 `revision` 비교 부분을 확대한다.

### 2.2 처음 등장할 때와 다시 등장할 때

| 시점 | 화면 | 청중이 하는 일 |
|---|---|---|
| 강의 시작 | 오늘 답할 질문과 짧은 키워드 지도 | 이미 아는 말과 새로 배울 말을 구분 |
| 첫 동작 직전 | 필요한 1–2개 용어를 한 문장과 작은 예제로 정의 | 용어를 대상·값과 연결 |
| 실제 동작 | 같은 용어를 해당 값이나 도해 가까이에 붙이고 변화 부분을 강조 | 어떤 조건이 어떤 결과를 만들었는지 설명 |
| 다른 조건의 사례 | 라벨 일부나 결과를 잠시 가림 | 배운 용어로 다음 결과를 예측 |
| 강의 마지막 | 처음의 지도를 다시 보여주되 관계 일부를 비움 | 용어와 관계를 자기 말로 복원 |

첫 화면에 모든 정의를 쏟아내지 않는다. 전체 목록은 방향 안내로만 짧게 제시하고, 필요한 정의는 해당 메커니즘을 보기 직전에 풀어 준다. 각 핵심 키워드는 정의, 적용, 회상에 다시 등장한다. 반복 시 동일한 설명을 읽기보다 입력이나 질문을 바꾼다.

### 2.3 자연스러운 연결

화면 전환에는 다음 개념이 필요한 이유가 있어야 한다. 작업 강의에서는 “현재 조건을 알았다”가 “어디까지 진행했는가”로 이어지고, “두 수정이 동시에 일어나면”을 통해 리비전이 필요해진다. 카탈로그에서는 “조건에 맞는 후보를 찾았다” 다음에 “다음 실행에서도 같은 내용을 쓰는가”를 물어 버전과 해시로 넘어간다.

장면별 전환 문장은 아래 표에 적었다. 발표자 노트에 유지하되 청중 화면에는 모두 인쇄하지 않는다. 전환할 때 직전 도해의 위치·대상·식별자를 유지하고 필요한 부분을 확대한다. 이전 그림을 다시 쓰는 경우에는 비교하거나 추적하는 학습 목적을 명시한다.

## 3. 집중을 환기하면서 흐름을 유지하는 규칙

강의의 의미 있는 경계에서 관찰·예측·설명·실행·회상으로 청중의 활동을 바꾼다. 4–6분 장면을 기본 단위로 설계했지만, 이는 편집상의 호흡이며 인간의 집중 시간이 고정돼 있다는 주장이 아니다. 설명 중간에 타이머에 맞춰 효과를 삽입하지 않는다.

| 방법 | 사용할 지점 | 실행 방식 | 흐름을 지키는 조건 |
|---|---|---|---|
| 결과 먼저 보기 | 이미지·영상 도입, 실제 출력 소개 | 결과를 10–20초 관찰한 뒤 볼 위치를 질문 | 그 결과를 만든 입력을 바로 이어 설명 |
| 차이 찾기 | 버전·해시, 구도, 검색 결과 | 처음에는 동일해 보이는 두 대상을 비교 | 차이가 있는 한 필드나 영역에 집중 |
| 결과 예측 | 동시 수정, 참조 파일 변경 | 답을 공개하기 전 10–20초 생각할 시간 | 처음 배우는 규칙을 맞히게 하지 않고 배운 규칙 적용 |
| 단계 공개 | 상태 전이, 입력 대응 | 원인과 변화 순서대로 2–3단계 공개 | 전체 지도가 먼저 보이고 위치를 유지 |
| 짧은 화면 녹화 | 등록·검색·퇴역, 코드 실행 | 필요한 조작과 출력만 20–60초 제시 | 녹화 전 볼 항목 하나를 지정하고 끝나면 해석 |
| 영상 재생과 정지 | 샷 경계, 연속성 | 8–15초 장면을 재생한 뒤 경계 프레임 정지 | 재생·슬로모션·정지의 목적을 구분 |
| 하이라이트 | 코드·로그·표·시간선 | 현재 줄이나 변한 값만 표시 | 강조를 옮기며 색만으로 의미를 전달하지 않음 |
| 짧은 적용 활동 | 정상 동작을 이해한 직후 | 값 하나 바꾸기, 필드 연결하기, 수정 범위 고르기 | 결과가 이어지는 설명의 입력이 됨 |
| 회상 | 장면 묶음의 끝, 강의 말미 | 개념 지도 빈칸이나 1문장 설명 | 공개 지목·점수 경쟁 없이 생각할 시간 제공 |

화면의 모든 요소를 동시에 움직이지 않는다. 설명하는 동안 배경 음악을 틀지 않으며, 영상 소리는 시간적 특성이나 오디오 검수 자체를 설명할 때 사용한다. 영상 중에는 긴 설명문과 음성 설명을 겹치지 않는다. 자막·전사와 정지 화면 대체 자료를 준비한다. 질문이 연속으로 반복되면 다음 구간은 짧은 시연이나 비교로 바꾼다.

## 4. 강의 00 — 전체 구조

**중심 질문:** 에이전트가 한 번의 응답을 넘어 일을 이어가려면 무엇을 관리해야 하는가?

**사례:** 문서 검토 작업의 진행·근거·수정 관계를 설명용 사례로 사용한다. 실제 실행 증거는 공개 참고 구현의 DB와 보고서로 구분해 보여준다. 마지막 응용 구간에 LUMA를 짧게 연결한다.

| 키워드 | 강의에서 사용할 정의 | 눈으로 확인할 대상 |
|---|---|---|
| 역할 | 시스템의 각 부분이 맡는 책임과 주고받는 것 | 다섯 분야의 책임 지도 |
| 상태 | 지금 무엇이 가능하고 무엇을 확인해야 하는지 나타내는 현재 조건 | 작업의 `state`와 관찰된 결과 |
| 근거 | 판단에 사용한 자료와 그 출처·적용 범위 | 원문, 출처, 선택 이유 |
| 계약 | 주고받는 자료가 갖춰야 할 필드·조건·검증 규칙 | 입력값과 수락·거부 조건 |
| 산출물 | 작업이 남긴 결과와 그 결과를 식별·확인할 기록 | 결과 파일, DB, 보고서 |
| 추적 | 결과에서 사용한 입력·자원·판단으로 관계를 따라가는 것 | 결과와 입력 참조의 연결 |

| 장면 | 분 | 키워드와 핵심 설명 | 화면·청중 참여 | 다음 연결 |
|---|---:|---|---|---|
| O01 | 3 | 역할: 응답 후에도 관리할 일이 남는다 | 검토 보고서가 수정 요청을 받은 두 시점을 크게 비교. 무엇을 다시 확인할지 15초 생각 | 다시 확인할 책임을 나눠 본다 |
| O02 | 4 | 역할: 다섯 분야의 책임 | 한 장의 관계 지도를 공개하고 공통 기반과 제작 분야를 구분. 고정 실행 순서로 그리지 않음 | 책임을 나눠도 현재 상황을 공유해야 한다 |
| O03 | 4 | 상태: 현재 조건 | 같은 작업의 진행 전후를 비교하고 현재 가능한 행동만 표시 | 상태 판단에는 자료가 필요하다 |
| O04 | 4 | 근거: 판단의 출처 | 날짜·적용 버전이 다른 문서 두 개. 답을 고른 이유를 짧게 설명 | 근거를 다음 단계가 읽을 형태로 전달한다 |
| O05 | 5 | 계약: 전달 조건 | 입력 객체의 필요한 세 부분을 확대. 필드 하나가 빠진 경우를 예측 | 전달 조건이 있어야 실행할 자원을 고를 수 있다 |
| O06 | 5 | 역할·계약: 카탈로그의 연결 | 후보 목록에서 작업·런타임 조건이 맞는 항목을 남기는 개념도 | 선택된 자원으로 결과를 만든다 |
| O07 | 5 | 산출물: 결과와 기록 | 공개 데모의 결과 파일·DB·보고서를 실제로 열어 필요한 부분만 녹화 | 결과가 생긴 뒤에도 연결이 남는다 |
| O08 | 5 | 추적: 결과의 출발점 | 같은 결과에서 입력·선택·근거로 되짚는 선을 순서대로 강조 | 일부가 바뀌면 어떤 결과를 다시 확인할까 |
| O09 | 5 | 추적·상태: 수정 범위 | 참조 하나를 바꾼 관계도. 청중이 재확인 범위를 고른 뒤 이유 공개 | 같은 구조가 제작 작업에도 적용된다 |
| O10 | 4 | 역할·계약·산출물: 이미지와 영상 | LUMA 이미지와 짧은 교육용 영상의 구도·시간 조건 비교. 제작 도구 자체보다 전달 관계에 집중 | 사례를 벗어나 구조만 다시 남긴다 |
| O11 | 4 | 여섯 키워드의 관계 회상 | 처음 지도에서 라벨 두 개와 연결 하나를 가림. 자기 작업을 지도에 대입 | 각 분야에서 더 자세히 볼 질문을 남긴다 |
| O12 | 2 | 역할: 주제별 학습 경로 | 다섯 강의가 답할 질문을 한 줄씩 제시 | 질의응답 10분 |

**도달 확인:** “상태는 작업, 근거는 지식”처럼 명칭만 연결하는 데서 끝내지 않고, 한 결과에 어떤 계약·산출물·추적 관계가 필요한지 설명할 수 있는지 확인한다.

## 5. 강의 01 — 작업

**중심 질문:** 여러 실행과 수정이 겹쳐도 다음 행동을 어떻게 결정하는가?

**사례:** 두 작업자가 같은 작업을 수정하고, 계획 변경과 응답 중단이 이어지는 상황. LUMA의 제품 맥락은 사용하지 않는다.

| 키워드 | 강의에서 사용할 정의 | 구분·보조 용어 |
|---|---|---|

| T08 | 5 | 복구: 결과 불명 | 실행 요청·응답 중단·결과 조회의 시간선을 화면 녹화와 함께 설명 | 결과를 확인한 뒤 상태를 조정한다 |

**도달 확인:** 상태와 단계의 차이, 오래된 수정의 거부 이유, 계획 변경 뒤 승인 처리, 결과 불명 뒤 조회가 필요한 이유를 설명한다. 핵심 구현을 본편에서 본 뒤 전체 함수와 운영 그래프 자료를 부록으로 제공한다.

## 6. 강의 02 — 지식

**중심 질문:** 자료를 모으는 것에서 재사용할 근거를 관리하는 것으로 어떻게 이어지는가?

**사례:** 적용 버전이 다른 두 기술 문서와 검색에서 계속 발견되는 오래된 설명. 공개 실습에는 합성 문서와 실제 문자열 검색을 사용한다.

| 키워드 | 강의에서 사용할 정의 | 눈으로 확인할 대상 |
|---|---|---|
| 출처 | 정보가 어디에서 왔으며 어떤 맥락에 적용되는지 확인할 단서 | 원문 위치, 작성 시점, 적용 버전 |
| 정규화 | 다른 형식의 자료를 정해진 필드와 표현으로 맞추는 처리 | 원문과 공통 필드의 대응. 내용의 참을 보장하지 않음 |
| 등록 | 식별자와 필요한 메타데이터를 갖춘 항목을 관리 대상에 넣는 과정 | 등록 레코드와 저장 성공 |
| 인덱스 | 저장된 자료를 찾기 위해 별도로 구성하는 검색용 표현 | 원문·등록 정보·검색 표현의 관계 |
| 검색 | 질문이나 검색어에 맞는 후보를 찾아 제시하는 과정 | 실제 검색어와 반환 결과 |
| 갱신 | 기존 지식의 내용·적용 조건·참조를 새로운 정보에 맞게 바꾸는 과정 | 새 판본과 관련 검색 경로의 재확인 |
| 퇴역 | 기록을 남기면서 현재 재사용 대상에서 제외하는 처리 | 저장된 항목과 현재 검색 결과의 차이 |

## 7. 강의 03 — 카탈로그

**중심 질문:** 이름을 선택하는 행위를 실행할 수 있는 구성의 선택으로 어떻게 구체화하는가?

**사례:** 이름은 비슷하지만 작업·런타임·버전·내용이 다른 템플릿 후보. 인기나 추정 품질 순위는 만들지 않는다.

| 메타데이터 | 자산의 종류·상태·지원 조건·참조를 설명하는 정보 | 카탈로그 항목의 필드 |

| 선택 | 조건에 맞는 자산을 특정 항목으로 결정하는 과정 | 남은 후보와 탈락 이유 |

| 해시 | 내용을 계산해 얻어 내용 변경 여부를 비교하는 값 | 메타데이터·템플릿 digest. 품질 평가 점수가 아님 |
| 바인딩 | 외부 입력 필드를 실행 템플릿의 특정 입력 위치에 대응시키는 선언 | 필드와 노드 입력 슬롯 |

## 8. 강의 04 — 이미지

**중심 질문:** 원하는 장면을 실행 입력으로 표현하고 원하는 결과가 나왔는지 어떻게 확인하는가?

**사례:** LUMA 램프와 문구 공간. 실제 또는 교육용 이미지의 제작 출처를 기록한다. 공개 참고 구현은 이미지 생성 모델을 실행하지 않으므로, 시각 사례와 컴파일 실습의 증거를 구분한다.

## 11. 대표 장면의 실제 연출 상세 — T04 리비전, 6분

이 장면은 강의 전체를 같은 판형으로 만드는 템플릿이 아니라, 정의와 시각적 동작이 연결되는 정도를 보여주는 제작 기준이다. 최종 슬라이드 번호는 전체 편집 때 정한다.

| 시간 | 화면 문구·배치 | 발표와 공개 동작 |
|---|---|---|
| 0:00–0:40 | 제목 `리비전` / 정의 `변경 전후를 구분하는 상태의 번호` / 가운데 `rev 7` | 번호가 품질 점수나 진행률이 아님을 짧게 설명 |
| 0:40–1:30 | 같은 위치의 rev 7, 양쪽 A와 B가 읽은 값 | 두 작업자가 같은 시점의 상태를 읽었음을 선 두 개로 표시 |
| 1:30–2:20 | A의 변경만 활성화, 현재 값 `rev 8` | A가 먼저 반영된 뒤 중앙 값만 변함. B가 가진 7은 그대로 유지 |
| 2:20–2:50 | B의 수정 요청, 결과 영역 비움 | “B의 요청은 반영될까요?” 15초 생각하고 이유를 짧게 받음 |
| 2:50–4:00 | `요청 7`과 `현재 8`을 가까이 배치, `거부` 공개 | 비교 후 갱신(CAS)을 보조 용어로 소개. 값의 불일치에 밑줄·라벨 병행 |
| 4:00–5:10 | 실제 코드의 리비전 비교와 해당 오류 출력 | 시각 설명과 코드의 비교 위치를 같은 강조색으로 연결. 전체 함수는 이 장면에 축소 배치하지 않음 |
| 5:10–6:00 | 같은 도해에서 두 번째 요청이 최신 번호를 가진 경우 | “번호가 맞으면 항상 실행 가능한가?”를 남겨 전이 조건·승인 설명에 연결 |

A·B와 번호는 설명용 값이다. 실제 실행 녹화는 공개 Store에서 얻은 값을 사용하며 화면의 사건 순서를 일치시킨다. 자동 반복 애니메이션은 사용하지 않고 발표자가 단계마다 진행한다. 강의의 마지막 공개 단계에서 비교 결과를 충분히 확인할 수 있게 한다.

## 12. 디자인 체계

실제 제작에서 사용할 화면 배치·색·서체 크기·주제별 대표 연출·움직임·10분 연속 시안은 [아트 디렉션과 화면 연출 설계](art-direction.md)에 구체화했다. 도입과 일반 설명 화면의 세부 규격은 이 문서를 따른다. 핵심 용어와 72개 장면의 학습 순서는 본 문서를 유지한다.

### 12.1 시각 방향

큰 한글 제목과 정교한 기술 도해를 중심으로 구성한다. 도입·장 전환은 짙은 남색, 설명은 따뜻한 흰색을 기본으로 한다. 코발트 블루는 현재 읽는 값·연결, 호박색은 차이·거부를 강조한다. 다섯 분야마다 무조건 다른 무지개색을 배정하지 않는다. 분야 이름과 고유한 도해 구조로 구분한다.

16:9, 기준 화면 1920×1080. 제목 72–96px, 중심 문장 40–52px, 주요 도해 라벨·코드 32–40px를 출발점으로 한다. 한글이 온전히 들어 있는 한 서체 가족의 굵기·크기·간격으로 위계를 만든다. 실제 투사·화면 공유에서 확인하고, 정보가 많으면 화면을 나눠 글자를 유지한다. 코드의 넓은 빈 공간을 장식 카드로 채우지 않는다.

키워드 첫 등장에는 큰 제목과 짧은 정의를 둔다. 이후에는 도해나 값 가까이에 짧은 라벨로 반복한다. 화면 상단에 전체 키워드 목록과 진행률을 계속 두지 않는다. 묶음이 바뀌는 지점에서 작은 개념 지도에 현재 관계를 표시한다.

### 12.2 내용에 따른 화면 구성

| 화면 유형 | 구체적인 구성 | 사용할 강의 |
|---|---|---|
| 개념 정의 | 큰 핵심 용어, 한 문장 정의, 실제 대상 하나 | 전 강의의 새 키워드 |
| 관계 지도 | 필요한 객체와 직접 붙인 라벨, 읽는 관계만 강조 | 전체, 지식, 카탈로그 |
| 상태·시간 변화 | 객체 위치 고정, 값과 시점의 변화 공개 | 작업, 영상 |
| 비교 | 동일 축척·기준의 두 결과와 차이 영역 | 지식, 카탈로그, 이미지, 영상 |
| 입력·출력 대응 | 원본과 도착점을 넓게 배치, 한 연결씩 읽기 | 카탈로그, 이미지 |
| 코드·실행 증거 | 4–6줄 핵심 코드 뒤 해당 출력 확대 | 분야별 실제 구현 |
| 이미지 중심 | 큰 실제 결과, 필요한 영역만 오버레이 | 이미지 |
| 영상·시간선 | 큰 재생 화면, 길이에 비례한 트랙과 현재 위치 | 영상 |
| 회상 | 익숙한 지도에서 일부 관계만 가림 | 전 강의 |

변화의 순서를 이해하는 애니메이션만 사용한다. 나타남·강조의 길이는 우선 150–350ms 범위에서 시험하고, 값 비교에 시간이 필요하면 발표자가 충분히 멈춘다. 수치는 취향·가독성 검토용 초기값이다. 자동 진행·장식 회전·지속 깜빡임을 사용하지 않는다. 축소 동작 환경에는 정적 표시를 제공한다.

## 15. 제작 순서와 파일 구성

1. **키워드 원고:** 이 설계의 용어를 공통 사전으로 고정한다. 각 장면의 목표·정의·화면 문구·발표 노트·질문·답·출처·시간을 작성한다.
2. **대표 시안 6개:** O02 역할 지도, T04 리비전, K09 검색 전후, C06 버전과 해시, I03 구도, V06 연속성을 실제 슬라이드와 필요한 자산으로 만든다. 이미지·영상 강의의 품질도 이 단계에서 확인한다.
3. **연속 구간 시연:** T03–T06과 I09–I12를 각각 이어 발표해 용어 도입·변화·회상이 자연스러운지 확인한다. 개별 화면의 미감만으로 확장하지 않는다.
4. **전체 강의와 작업 강의:** 시스템 공통 용어와 기술 깊이를 먼저 확정한다. 전체는 약 24장, 분야별은 약 30장을 출발점으로 하되 장면의 필요와 리허설에 따라 조정한다. 정의·도해·실행을 한 장에 과밀하게 합치지 않는다.
5. **나머지 네 강의:** 지식·카탈로그·이미지·영상을 만들고 공통 용어의 표기와 구현 근거를 교차 확인한다. 필요한 코드·스키마·추가 실습은 각 강의 부록으로 제공한다.
6. **리허설·교정·배포:** 각 강의 시간과 참여 구간을 재고 실제 표시·재생·질문 대응을 확인한다. GitHub Pages에 강의별 HTML, 발표자 노트와 로컬 미디어를 제공한다. 웹 강의를 주 배포 형식으로 사용한다.

예정 경로는 `/slides/overview/`, `/slides/tasks/`, `/slides/knowledge/`, `/slides/catalog/`, `/slides/image/`, `/slides/video/`다. `/lectures/` 목록은 강의 선택을 위한 페이지이고, 강의 화면은 고정 비율의 발표 화면이다. 블로그 `/blog/`와 위키 `/wiki/`는 읽기·참조 역할을 유지한다. 여섯 강의의 구현 경로다. 강의 선택의 주 진입점은 `/lectures/`다. 배포 검증은 [강의 검토 기록](../publication/lecture-validation.md)에 남긴다.

HTML은 reveal.js의 발표자 노트·단계 공개·미디어 재생 기능을 사용한다. 실제 제작 시 버전과 자산을 고정하고 오프라인 재생을 확인한다. 핵심 원고에는 `course_id`, `scene_id`, `keyword_ids`, `learning_goal`, `on_screen`, `speaker_notes`, `visual_asset_ids`, `reveal_steps`, `question`, `answer`, `bridge`, `duration_seconds`, `evidence`, `offline_fallback`을 기록해 내용·시각·시간을 함께 관리한다. 이 설계를 기준으로 HTML 강의를 구현하고 화면·재생·발표자 제어를 검증한다.

청중 검토가 가능하면 처음 보는 사람에게 대표 장면의 핵심을 설명하게 하고, 조금 뒤 새 조건에 같은 개념을 적용하게 한다. 틀린 답을 학습자의 문제로 처리하지 않고 용어·순서·시각 표현의 수정 근거로 기록한다. 자동 검사, 자체 검토, 실제 청중 검토를 구분해 남긴다. 현재 이 문서에 적은 집중·이해 효과는 설계 목표이며 아직 측정한 결과가 아니다.

## 17. 참고한 학습·발표 원칙

- [Mayer — Pre-training Principle](https://www.cambridge.org/core/books/abs/multimedia-learning/pretraining-principle/01791D57F5D4164251269E6DF56A8BF1): 주요 개념의 이름과 특성을 먼저 이해하도록 돕는 원칙을, 동작 직전의 짧은 정의에 반영했다.
- [Mayer & Fiorella — Coherence and Signaling](https://www.cambridge.org/core/books/abs/cambridge-handbook-of-multimedia-learning/principles-for-reducing-extraneous-processing-in-multimedia-learning-coherence-signaling-redundancy-spatial-contiguity-and-temporal-contiguity-principles/CD5B7AE1279A9AB81F8EEBB53DBEC86E): 불필요한 정보를 덜고 중요한 구조를 가리키는 신호를 주는 원칙을 매체 선택과 강조 규칙에 적용했다.
- [Cambridge Handbook — Segmenting, Pre-training, Modality](https://www.cambridge.org/core/books/abs/cambridge-handbook-of-multimedia-learning/principles-for-managing-essential-processing-in-multimedia-learning-segmenting-pretraining-and-modality-principles/DD24C2F48B9B1277CE59F78276110258): 복잡한 설명을 나누고 청중이 처리할 틈을 두는 설계에 참고했다. 연구의 학습자 조절 조건을 강의자의 단계 공개와 동일한 효과라고 단정하지 않는다.
- [Duarte — Presenting](https://www.duarte.com/blog/presenting/), [Presentation Zen — Signal-to-noise](https://presentationzen.com/blog/the-signal-to-noise-ratio-activity): 장면의 중심 생각과 시각 증거를 명확히 하고, 정보에 기여하지 않는 요소를 줄이는 편집에 참고했다.
- [reveal.js — Speaker View](https://revealjs.com/speaker-view/): 발표자 화면과 배포 형식을 구분할 구현 근거다.

키워드 개수, 강의 시간, 장면 길이, 시안 순서와 화면 수치는 p-hermes를 위한 편집안이다. 연구가 보장하는 최적 수치나 검증된 집중도 지표로 제시하지 않는다.
